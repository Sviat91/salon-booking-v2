## Decisions Made

- **Redesign admin pages one at a time, never batched** — user explicitly confirmed this mid-session specifically so bugs stay easy to isolate to a single stage; validated by this session's own experience (the calendar stage alone needed 4 follow-up bug-fix rounds after "completion").
- **`SettingsSection` reusable wrapper** (`src/app/admin/settings/FormFields.tsx`) — extracted during Stage 6 to deliver the card+header-bar visual AND to keep `SettingsForm.tsx` under the 500-line limit; reused as-is (not duplicated, not promoted to `src/components/admin/`) for Stage 7's Email page, accepting a minor cross-directory import-layering smell rather than risk touching already-approved Stage 6 files.
- **Two independent, must-never-cross-wire color systems**, clarified during the Masters stage: the tenant brand color (`TenantConfig`, semantic tokens like `bg-primary`) vs. each master's own per-master `color` DB field (used only via inline `style`, e.g. the avatar ring — never rendered through a tenant-customizable class, or all masters would collapse to one hue).
- **Raw `--md-*-container` fixed tokens are for status-pill-style elements only; tenant-customizable semantic tokens are correct for page/form chrome** — this distinction is re-assessed fresh per page rather than mechanically reapplied. Confirmed this session that Settings/Email pages have no status pills, so no `--md-*` fixed tone was introduced there (correctly different from the calendar's day-off/shift pills).
- **Design mockup coverage is often partial — verify before trusting it, every stage.** Services, Masters, and especially Settings/Email all found the mockup depicted only a subset (or, for Email, nothing at all — just a placeholder) of the real page. Each plan named this explicitly and extrapolated the already-established visual language rather than inventing unfounded new details.
- **`darkCardColor` default corrected** from `#211A1B` to `#22160f` (both `src/lib/tenant.ts`'s fresh-install seed and `SettingsForm.tsx`'s "Reset to M3 defaults" target) after the user manually verified the better value worked in their own live tenant settings. `prisma/schema.prisma`'s separately-stale `#2A2A2A` DB-column default was left untouched — confirmed dead code (`getTenantConfig()` always explicitly provides all fields), fixing it would need an unnecessary migration for zero functional benefit.
- **Standing "no dev server" rule upheld all session** — every stage's automated verification was `tsc --noEmit` + `npm run lint` + `npm run build` only; anything requiring visual/interactive confirmation was handed to the user as an explicit manual checklist.
- User manually deleted several now-completed `handoff/*_plan.md`/`*_feedback.md` files during this session (working-tree state, not a tool action) — consistent with `handoff/AGENTS.md`'s note that these are working documents for a feature's lifecycle, not a permanent log, and may be cleaned up once shipped.
