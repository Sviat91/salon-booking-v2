## Decisions Made

- **Admin/master manually-created bookings now trigger the same instant Telegram notification as client bookings** — the user explicitly wants staff-created bookings visible to whoever manages the salon via Telegram, not just client-initiated ones.
- **24h/2h reminders are client-only; the salon gets zero reminder pings** — only the instant creation/cancellation/update notification. Explicit user correction after initially building it the other way (migrate reminders to broadcast) — corrected mid-session before implementation.
- **Multi-recipient chat IDs use a real DB table with add/remove UI, not a comma-separated string** — user explicitly rejected the string-based approach as error-prone/non-obvious.
- **No automatic backfill of the old single `notifAdminChatId` value** into the new recipient table — accepted tradeoff at this dev stage (no production data yet), user re-added their chat ID once via the new UI.
- **`notifyBookingReschedule` broadened into `notifyBookingUpdate`, covering service changes too** — one unified "something about this booking changed" notifier rather than a near-duplicate function, after the user found that procedure-only edits were silently not notifying anyone.
- **Actor labels stay in the existing hardcoded-Polish message convention** (no i18n introduced for notification bodies) — matches the project's already-deferred decision to not fix the bot's Polish-only notification language this session.
- **Master actor is named in notifications** (e.g. "Mistrz Anna"), client/admin stay generic ("Klient"/"Administrator") — a salon can have multiple masters, so naming disambiguates; no such ambiguity exists for the other two roles.
