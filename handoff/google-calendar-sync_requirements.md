# Google Calendar two-way sync — requirements brief (orchestrator → planner)

Mode: FULL. Written 2026-09-21 after a Q&A with the user (all decisions below are LOCKED by the user unless marked "ORCHESTRATOR DEFAULT — confirm").
Deliverable from the planner: `handoff/google-calendar-sync_plan.md` — staged, checkbox-based, each stage independently shippable; the user verifies manually after each stage (project rule: stop after every stage).

## Why

A master (Юля) asked: "what if I'm offline and can't see my schedule?" Building a native app is too expensive. Instead: sync each master's bookings with her Google Calendar (the Google Calendar phone app works offline), and pull back what she changes there.

## Locked decisions

1. **Auth = ONE Google service account per salon instance** (each client salon is its own deployment). The user/operator creates the Google Cloud project + service account + JSON key once per salon and pastes the key into admin Settings. Key must be stored **encrypted via `src/lib/encryption.ts`** and never rendered back into the page (same rule as SMS/SMTP credentials). Not OAuth (rejected: Google app verification, refresh-token expiry, per-master friction).
2. **Per-master opt-in.** A calendar ID is stored per master. It can be entered by **the master herself (her own panel) AND by ADMIN/SUPERADMIN** for any master. The master (or whoever owns the calendar) shares it with the service-account email with "Make changes to events". Disconnect = clear the ID → sync stops. Salon-side ownership of data is the point: when a master leaves, the salon just disconnects/reassigns.
3. **Site → Google (push).** Every appointment create / update (time, procedure, status) / cancel / delete on the site creates/patches/deletes the Google event. Event **title = the same two things the site calendar shows: `<client name> — <procedure name>`** (procedure in the salon's default language). **Everything else (phone, price, notes, etc.) goes in the event description** (user confirmed phone is OK there). Set `extendedProperties.private` (e.g. `appointmentId` + a marker) so our own events are recognised on pull and echoes can be suppressed.
4. **Google → site (pull), FULL sync for site-made events:** if the master moves/resizes a site-made event in Google → update the appointment's time on the site **and send the usual change notification** (existing `notifyBookingUpdate` path, with an actor such as "Google Calendar"; client is notified like any time change). If she deletes it in Google → cancel the appointment on the site through the existing cancellation path (+ notifications). *ORCHESTRATOR DEFAULT — confirm:* edits of the event's **title/description text** on a site-made event are NOT applied back (client name/procedure come from the client/service records; we must not rewrite client data from free text); only time and deletion sync back.
5. **Events created directly in Google (foreign events)** — e.g. she quickly blocks time or writes "Anna body massage" offline. They become **read-only "external blocks"** (NEW table; an `Appointment` requires a client + service so they cannot be Appointments). They:
   - **block availability** (`src/lib/availability.ts`) and the conflict checks inside booking/manual-create/update-time transactions, for that master;
   - **appear in the site calendar (Month/Week/Day/Agenda, admin + master views) rendered exactly like an appointment**: first line = event **title**, second line = **first line of the event description** (truncate ~80 chars). Missing title → localized fallback "Google Calendar event"; missing description → localized fallback "Added via Google Calendar" (pl/en/uk). **Store the raw title/description (nullable) and resolve the fallback at display time in the viewer's language** — do not store translated fallback text. If neither exists, show only the fallbacks.
   - are read-only on the site (edit them in Google; the next sync brings the change). Opening one shows a read-only view (time, title, description, "from Google Calendar"). Planner may propose a Delete action that also deletes the Google event, but keep v1 minimal.
   - generate **no** reminders, client notifications, price/revenue stats, or GDPR client linkage.
   - Import rules: only **future** events (from today; never import history); skip cancelled and free/transparent events; expand recurring events (`singleEvents=true`); all-day events block the whole working day (planner to define exactly).
6. **Conflicts = notify only, never auto-delete/modify anything.** A conflict = a foreign event or a moved site event overlapping another appointment of the same master. Keep both, flag the conflict (red mark in the site calendar is desirable), and **notify wherever enabled**: existing Telegram recipients (`TelegramNotificationRecipient`, via `broadcastTelegram`), email if SMTP enabled; message must name master, both entries and times. (Per-master Telegram bots are a FUTURE task, not part of this.)
7. **First connect:** push all existing **future** site appointments to Google (backfill); import only **future** Google events. Past is ignored both ways.
8. **Frequency:** poll roughly every 60 s per connected master using Google's incremental sync (`syncToken`; handle 410 by full re-sync), **plus an immediate push** on every site mutation. Scheduler runs **in-process**, started from `src/instrumentation.ts` like the Telegram client bot (`src/lib/telegram-bot/lifecycle.ts`) — no host cron changes (existing instances only have an hourly reminders cron). Must be safe against double start (HMR/dev), overlapping ticks, and must never crash boot.
9. **Timezone:** use the single `SCHEDULE_TZ` constant (`src/lib/schedule-utils.ts`, currently `Europe/Warsaw`) for all event start/end conversions so a later per-tenant timezone task can swap it in one place (Ukraine launch is a separate backlog item).

## Staging (must be independently shippable)

- **Stage 1 — connection + push (site → Google).** Settings UI for the service-account key (encrypted, with an instructions panel like `SmsInstructions.tsx`: Google Cloud project, enable Calendar API, create service account + key, share calendar with the SA email), master-panel + admin field for the calendar ID with a "test connection" / status indicator and clear error surfacing (invalid ID, no access, quota, revoked key), the Appointment↔event mapping, push on all appointment mutations, first-connect backfill of future appointments, failure handling/retry so a Google outage never breaks booking. This alone already solves the offline-viewing problem.
- **Stage 2 — pull (Google → site).** Scheduler, incremental sync, echo suppression, site-made event time-change/delete → appointment update/cancel + notifications, foreign events → external blocks, availability + booking-conflict integration, calendar rendering of blocks in all views, conflict detection + notifications.
- Consider a possible later Stage 3 (not in scope now): service account creating the calendar and sharing it to the master's email automatically.

Also the GDPR erase path (`src/lib/consent-service.ts` and the erasure API) — erasure of a client **must scrub PII from their Google events** (planner: decide how).

## Open design questions the planner must decide (and justify briefly)

1. Central mutation hook (Prisma `$extends` vs explicit service call) and failure/retry strategy (outbox table vs best-effort + periodic reconcile).
2. Library choice (see above).
3. Data model: `MasterProfile` fields (calendar ID, syncToken, status/lastError/lastSyncAt), `Appointment.googleEventId` (+ etag/updated for echo suppression), `ExternalCalendarBlock` (raw title/description, start/end, googleEventId, masterId, conflict flag), tenant-level SA credentials fields.
4. Echo suppression (our own push coming back on the next incremental pull) and loop prevention.
5. Conflict representation + how the calendar shows it; dedup so the same conflict does not notify every minute.
6. Scheduler design (interval, jitter, overlap lock, per-master error isolation, backoff on quota/401/403/404/410, HMR-safe singleton, disabling when no SA key configured).
7. All-day + multi-day + recurring + timezone edge cases (`SCHEDULE_TZ`), events crossing midnight, DST.
8. Where the "external block" enters `availability.ts` and every transaction that checks for overlap.
9. Security: who may set/see the calendar ID; that the SA key/SA email is only shown to ADMIN/SUPERADMIN (email needed to tell masters whom to share with — the SA **email is not a secret**, the private key is); calendar-ID input validation.
10. Anything in this brief that is wrong or risky — say so at the top of the plan under "Assumptions to confirm".
