## Decisions Made

- **Bulk Editor color scheme (round 3, final): dot = working (master's color), stacked full-width colored lines = day off (one per off-master), no color-fill/wash for day-off at all.** Rejected a cell-fill approach because once hue means "master identity" it can't simultaneously mean "day-off state" — a day-off cell washed in a green-colored master's own color would read as "available", the opposite of the truth. Also rejected round 2's single-bar-split-into-segments as insufficiently legible (user's actual complaint that triggered round 3).
- **Target-master selection hard-capped at 5** (not a higher/lower number) — confirmed explicitly with the user via a clarifying question before planning, since it's a real product-capability change, not just cosmetic. "Apply to all specialists" is disabled-with-tooltip rather than silently truncated when the salon has more than 5 masters.
- **Photo drag handle is a dedicated grip icon, not full-tile drag** — the whole-tile approach was considered and rejected specifically because it requires `touch-action: none` on the tile, which at the mobile `grid-cols-2` breakpoint would block vertical page scroll over the photo grid on all 4 surfaces this component renders on.
- **`SortableList.tsx` generalized via a string-union `strategy` prop (`"list" | "grid"`) mapped internally to dnd-kit's actual strategy functions**, rather than accepting a raw dnd-kit `SortingStrategy` value — keeps `PhotoListEditor.tsx` importing nothing from `@dnd-kit/*` directly, preserving the file's own "single place dnd-kit is wired" contract.
- **Multi-file photo upload stays client-side batching against the unchanged single-file `/api/upload` endpoint** (no server-side multi-file support added) — N chunked requests (concurrency 3, bounding server-side memory from the route's whole-buffer-in-memory pattern) rather than one bigger endpoint change.
- **No new automated browser/visual testing was used anywhere this session** — per standing user instruction (memory: never open agent-browser without explicit in-message instruction), every round's UI correctness was verified by the user manually via screenshots after each implementation, with the orchestrator independently re-running `npm run lint`/`npm run test` (never `dev`/`build`, per the other standing memory about the user's live dev server).
