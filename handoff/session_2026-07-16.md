## Decisions Made

- **User explicitly rejected 3 different "simpler" approaches this session** in favor of more work-intensive but higher-quality alternatives: (1) horizontal-scroll toolbar instead of a width-locked layout — rejected, chose the width-lock; (2) Day-view-only mobile calendar instead of full parity — rejected, chose full Month/Week/Day rework; (3) horizontal-scroll mobile tables instead of cards — rejected, chose a shared `DataCard` component. Consistent theme: user prioritizes matching established mobile-app UX conventions (Google/Apple Calendar) over the cheapest implementation.
- **`w-[calc(100vw-240px)]` over any `max-w-*`/responsive-cap approach** for the admin content width — the only way to guarantee the sidebar toggle never visually resizes content, only re-centers it, is to derive the target width from the viewport directly with a hardcoded constant, not from "available space" (which itself depends on the sidebar's current state).
- **Card-per-row mobile tables via one shared `DataCard` component, not per-table bespoke layouts, and not a config-driven table-engine abstraction** — explicitly avoided over-engineering in either direction.
- **`DbBrowserClient.tsx` kept as a horizontal-scroll exception** to the card-table pattern — reasoned justification: arbitrary/many dynamic columns, SUPERADMIN-only diagnostic tool, cards would be unusably tall.
- **Settings mobile floating Save button reads the same single source of truth as the sidebar's existing Save button** (via the `settings-dirty` CustomEvent / local `isDirty` state) rather than an independent tracking mechanism — guarantees the two buttons can never disagree about unsaved-changes state.
- **When a bugfix investigation concludes "no bug found," treat that as provisional, not final** — this session had one such conclusion (homepage preview overflow) proven wrong by the user's repeat testing; the correct fix on the second attempt required going one level up the component tree from where the first investigation stopped. Worth remembering as a general debugging lesson for this project.
- **Coordinate-based portal positioning (`createPortal` + `useLayoutEffect` + `getBoundingClientRect()`) is now the established, repeatedly-proven pattern in this codebase** for any dropdown/popover that must render outside a narrow, scrollable, or clipped ancestor — used successfully for `TimePickerDropdown.tsx` (pre-existing), `MasterSelectDropdown.tsx`, and now `WeekDayEditPopover.tsx`. Default to this pattern immediately for any future "popover renders in the wrong place" bug rather than re-diagnosing from scratch.
