**Email case-insensitivity fix (login/forgot-password/register duplicate-check).** `src/auth.ts`'s `authorize()` looked up `User.email` with an exact-case match, while `/api/auth/register` normalizes to lowercase on insert — any casing mismatch between registration and login made an account permanently unfindable, read as "wrong password", and wasn't fixed by a password reset (the email lookup, not the password, was mismatched). Fixed via `` prisma.$queryRaw`WHERE LOWER(email) = ${normalized}` `` (not just lowercasing the login input — `createMaster`/`scripts/create-admin.ts` don't normalize on creation, so a plain `.toLowerCase()` on only the login side risked breaking already-working logins for accounts with mixed-case stored emails). Applied the same fix to `forgot-password` and `register`'s duplicate-email check. Updated `tests/app/api/auth/register.route.test.ts`'s mocks (`$queryRaw`, `findUnique`) to match. **Not confirmed as the actual fix for tonight's live bug** — see Blockers.

**A real regression I introduced and reverted same session:** briefly removed `LoginForm.tsx`'s client-side "wait for Turnstile token before submitting" guard, on the mistaken belief that `checkLoginGuards()`'s `requireToken: false` makes the server tolerate a missing token. Re-read `src/lib/turnstile.ts`'s `validateTurnstileForAPI` carefully: `requireToken: false` only skips the check when Turnstile is *unconfigured* server-side; when configured (as it is here), a missing token is *always* rejected with `TURNSTILE_TOKEN_REQUIRED`, full stop — the "fails open" behavior in the auth-guards comment refers only to a genuine Cloudflare verify-call network failure (`VERIFY_ERROR`), a different case. Removing the client wait meant a login attempted before the widget finished producing a token got silently rejected and shown as "invalid email or password". Reverted in full; the guard is back.

## Decisions Made

- **`register()` must never bind directly to `src/components/ui/input.tsx`** — it's not `forwardRef`-wrapped under React 18; use `Controller`/`FormField` instead, project-wide.
- **`isDirty`/dirty-tracking correctness matters more than avoiding a slightly-eager Save button** — accepted that typing-then-deleting in the recipients field now correctly re-disables Save (previously it didn't, due to the underlying `register()` bug).
- **Never spread `$queryRaw` results directly into typed Prisma call sites without a follow-up `findUnique`** — used a two-step id-then-fetch pattern in `auth.ts`/`forgot-password`/`register` to keep full type safety while getting case-insensitive matching that Prisma's SQLite connector can't do natively (`mode: 'insensitive'` is Postgres/MySQL only).
- **Booking-confirmation/reminder emails don't need a separate consent checkbox** — researched and confirmed transactional messages (no promotional content) are covered by GDPR's contract-necessity basis, not marketing consent. Checkbox removed from both booking and registration flows; underlying DB column (`consentNotificationsV10`) left alone, always recorded `true`.
- **`/admin/calendar/page.tsx` was deliberately left without its own page-level auth check** — it's client-only and its real data comes from an already-properly-gated API route, so the risk is materially smaller than the three pages that *were* fixed (which server-rendered real data with zero auth check at all).
- **This session ran without the planner/coder/reviewer pipeline** except for the Telegram-recipients fix specifically, which the user explicitly asked to escalate to FULL mode after 3 failed direct-fix rounds. Everything else (including tonight's still-unresolved login bug) was direct implementation, per the user's stated "we're not using the planner this session, limits are close" framing from earlier — worth checking with the user next session whether that constraint still applies.
