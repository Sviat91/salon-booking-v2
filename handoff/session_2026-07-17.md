## Decisions Made

- **Per-language DB columns (not a translations table), fixed to exactly the app's 3 existing i18next locales (pl/en/uk)** — locked with the user before implementation started; avoided building open-ended language infrastructure beyond what the app's own UI already supports.
- **`TenantConfig.enabledLocales` reused across three distinct purposes** rather than introducing separate config fields for each: admin content-authoring gating (Group B), the app-wide UI language switcher (Group E), and (implicitly) which languages an admin can pick when entering a service name/bio. Single source of truth, parsed everywhere via the same `parseEnabledLocales()`.
- **Client-facing notifications use the client's booking-time language; admin/salon-facing copies stay a fixed default (Polish).** This was a genuine correction mid-session: Group D originally resolved ALL notification copy to `DEFAULT_LANGUAGE`, on the (wrong) rationale that "there's no persisted per-client locale." The user pushed back hard ("это же бред") — the client's language WAS available at booking time, it just wasn't being captured. Group F added persistence (`Appointment.clientLanguage`) specifically because reminders fire from a cron job with no live session, so the language has to be stored, not resolved live. Admin/salon copy intentionally stays on a fixed default since there's no single reliable "admin language" for a salon-wide notification.
- **No privileged/default language anywhere in the enable-disable-languages feature** — second explicit user correction this session. Originally Polish was hardcoded as unremovable in the Settings checkbox, force-re-included on save even if unchecked, and used as the stale-session fallback target. Reworked to a fully generic "at least one enabled, any one" rule across all three call sites. Strong, general preference worth carrying forward: don't silently pick a "default" when the actual requirement is just "non-empty" — ask/generalize instead of privileging one option arbitrarily.
- **Content-authoring's NOT-NULL `name_pl`/`bio_pl` schema requirement was deliberately left untouched** despite the "no privileged default" pushback above — this is a different layer (DB schema constraint from Groups A/B, decided explicitly with the user at the time) from the UI-language-selection layer this session's fixes targeted. Flagged to the user as a possible follow-up, not decided either way.
- **`procedure-translator.ts` deleted outright, not kept as a fallback** — once structural per-locale columns existed and all call sites were migrated, the dictionary was fully dead code (project directive: remove dead code immediately, don't leave backwards-compat shims).
- **Every stagewise group ran through the full planner→coder→reviewer cycle** (FULL/LIGHT mode per CLAUDE.md), with the user verifying live and explicitly signing off before the next group started — no chaining. This surfaced two real bugs a purely automated pipeline likely would have missed (the notification-language cop-out, and the hardcoded-Polish-default framing) precisely because the user was actually using the feature between groups rather than approving on trust.
