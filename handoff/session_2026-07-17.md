## Decisions Made

- **Multilang architecture** (locked before implementation): per-language DB columns (not a translations table), fixed to the app's existing 3 locales (pl/en/uk), `TenantConfig.enabledLocales` reused across three purposes (content-authoring gating, UI switcher gating, and — implicitly — which languages an admin can enter content in) rather than separate config fields per purpose.
- **Client-facing notifications use the client's booking-time language; admin/salon copies stay a fixed default.** Corrected mid-session after the user rejected the original "notifications are always Polish" implementation as a cop-out — the client's language WAS available at booking time, it just wasn't being captured. Added `Appointment.clientLanguage`, persisted specifically because reminders fire from a cron job with no live session to read a language from.
- **No privileged default language anywhere in the enable/disable-languages feature.** Second explicit correction: Polish was originally hardcoded as unremovable/the fallback target in three places; reworked to a fully generic "at least one enabled, any one" rule. **General preference worth carrying forward into the bot work and beyond: don't silently pick a "default" when the real requirement is just "non-empty" — generalize instead of privileging one option arbitrarily.**
- **`procedure-translator.ts` deleted outright** once structural per-locale columns existed — no fallback shim kept.
- **Telegram bot: interactive native chat, not a Mini App.** I recommended a Mini App (reusing the already-polished, already-localized mobile web booking flow with far less new code) and the user firmly overruled it — a "normal"/proper bot is mandatory, non-negotiable. Noted for future: don't re-litigate this, it's settled.
- **Telegram bot: one deployable app, no n8n, no separate service.** Bot runs in-process via a grammy webhook (`POST /api/telegram/client-bot/webhook`), not polling — polling would need its own always-running process outside Next.js request/response handling, which conflicts with this constraint.
- **Telegram bot: booking creation reuses extracted shared logic, not an HTTP self-call.** The bot must not call the public `/api/book` endpoint (which may later gain Turnstile/CAPTCHA per an open ROADMAP item — a webhook bot can't complete a CAPTCHA). Instead, `src/app/api/book/route.ts`'s inline transaction gets extracted into a framework-free `createBooking()` callable from both the HTTP route and the bot.
- **Telegram bot: v1 = booking creation only.** Managing/cancelling an existing booking via the bot is explicitly deferred to a later phase, not designed now.
- **Telegram bot: wizard state in Redis** (existing Upstash connection via `src/lib/cache.ts`, 30-min TTL, no new DB table), **consent stays in-chat** (inline buttons, reusing `consent-service.ts`, not a link-out to the website), **phone via Telegram's native "request contact" button** (not typed), **bot text reuses the existing 3 locale JSON files** under a new `bot.*` namespace, **token stored in plaintext** (consistent with how the existing salon-notification bot's token is already stored — an intentional consistency choice, not a new regression, flagged as revisitable later for both bots together if encryption is ever wanted).
