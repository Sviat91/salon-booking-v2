## Decisions Made

- **Fade-mask stops must be fixed lengths (`rem`), not percentages**, whenever they need to align with a fixed-width reserved space — this is the actual fix behind the whole nav-bar saga from the prior session, not a magnitude tweak.
- **Use `agent-browser` (screenshot + pixel sampling + DOM measurement) for any further visual/animation disputes**, rather than iterating blind on CSS values and trusting `curl`-confirmed markup alone — this directly ended a pattern of wasted rounds from the previous session and was used successfully multiple times this session (nav fade verification, calendar-gap root-causing, D-1–D-4 stale-cache diagnosis).
- **Root-level `AnimatePresence` / the existing dead `PageTransition.tsx` must not be wired up** to solve entrance/exit animation asks — it would force sequential exit-then-enter behavior that breaks the existing shared-`layoutId` avatar-flight animation the user already approves of. Documented as an explicit trap in the plan file for future reference.
- **`Sheet` scroll fix applied at the shared `sheet.tsx` component level**, not per-consumer, after auditing all 12 usages — consistent with the prior session's precedent of shared-Sheet-level changes (the full-travel slide animation) being acceptable once every consumer is checked.
- **Widget entrance animations must be deliberately delayed to start *after* the primary content above them settles**, not fire simultaneously at mount — simultaneous-but-uncoordinated animations read as "jerky" even when each individual animation is smooth. General principle likely worth applying to any future staged-reveal UI in this app, not just these two widgets.
- **Homepage widget slot (Settings) only allows `photoWidget`**, not `photoGallery`; same restriction on the master footer slot (`photoWidget`/`text` only, no `photoGallery`). Full multi-photo galleries with lightbox require a separate content *page* (own URL, appears as a nav tab) — this is a deliberate, existing architectural split, not a gap, though the user's "full gallery pinned below the main page" idea (mentioned in passing) isn't currently possible without a dedicated follow-up if ever wanted.
- **Admin-managed per-master pages (Group 6) is scoped as its own new feature**, not a Round 2 correction — it needs new routes and new admin-scoped (not session-derived) server actions, unlike everything else this session which was fixing/tuning what already existed.
