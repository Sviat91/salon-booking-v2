8. ~~Google Calendar/Sheets ID через переменные окружения~~ — **сделано (2026-07-13).** Проверено: интеграция с Google Calendar/Sheets в живом коде отсутствует полностью — `/api/book` пишет только в БД + шлёт уведомление через `@/lib/notifications`, GDPR-согласия идут через `@/lib/consent-service` (Prisma), нигде в `src/` нет `googleapis`/`GOOGLE_CALENDAR_ID`/`GOOGLE_SHEET_ID`. Удалены мёртвые переменные из `.env.example`/`tests/setup/env.ts` и 6 тестов, которые падали, потому что тестировали несуществующий `src/lib/google/*`.

9. ~~Пароли мастеров хранятся в открытом виде (`plainPassword` в базе)~~ — **сделано (2026-07-14).** Финальный подход (заменил более раннюю в тот же день попытку просто удалить колонку): новая колонка `User.passwordEncrypted` хранит пароль мастера **зашифрованным** (AES-256-GCM через существующий `src/lib/encryption.ts`), рядом с bcrypt-хешем `password`, используемым для логина. ADMIN/SUPERADMIN может расшифровать и показать текущий пароль по явному клику "Show current password" — новый server action `getMasterPassword` (`src/app/admin/masters/actions.ts`) сам проверяет роль вызывающего. Шифротекст никогда не попадает в список мастеров/типы страницы, только внутрь этого action. GDPR erase/consent-service чистят новое поле, db-browser маскирует его.

10. ~~Ключ шифрования (`AUTH_SECRET`) может тихо остаться пустым~~ — **сделано (2026-07-14).** `src/lib/encryption.ts` теперь падает с явной ошибкой при импорте, если `AUTH_SECRET` не задан/пуст — больше нет тихого шифрования публично известным дефолтным ключом. Задокументировано в `.env.example`, задан плейсхолдер в `tests/setup/env.ts`.

## 🟡 Приоритет 3 — Не критично, но стоит сделать до продажи

- ~~Регистрация не ограничена по частоте — можно спамить аккаунтами.~~ — **сделано (2026-07-14).** `POST /api/auth/register` теперь rate-limited по IP (5 запросов / 15 минут) через уже существующий `rateLimit()` из `src/lib/cache.ts` — тот же паттерн, что у `forgot-password`/`reset-password`/GDPR-эндпоинтов. Проверка стоит первой строкой в `POST`, до парсинга тела запроса. План+ревью в `handoff/registration-rate-limit_plan.md`/`_feedback.md`.
  > **Найдена отдельная, более широкая проблема (не тронута в этом проходе):** `rateLimit()` в `src/lib/cache.ts` тихо "открывается" (разрешает всё), если Upstash Redis не настроен/недоступен — это касается уже всех 6 существующих rate-limited эндпоинтов, не только регистрации. Не критично, если Upstash всегда настроен в проде, но стоит закрыть отдельным заходом (in-memory fallback-счётчик, по аналогии с `cacheGet`/`cacheSet` в том же файле, которые такой fallback уже имеют).
- Проверка телефона гостя при отмене/переносе — только по последним 9 цифрам (не по полному номеру).
- `app.db` и файлы загрузок закоммичены в git (хотя в `.gitignore` `*.db` есть).
- Нет security-заголовков (CSP, X-Frame-Options и т.д.).
- Возможна гонка при двойном бронировании одного времени (низкая вероятность).
- Захардкоженная услуга-заглушка "Консультация" на русском в универсальном приложении.
- Мелкие несостыковки языка в текстах ошибок (польский/русский вперемешку).
