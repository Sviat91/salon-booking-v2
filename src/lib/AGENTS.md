# AGENTS.md — src/lib

## Purpose

Core business logic and services: booking availability, consent/GDPR handling, caching, notifications (email + Telegram + SMS), encryption, validation schemas, and misc utilities. This is the layer API routes and pages call into — it owns the rules, not the callers.

## Ownership

Anything framework-agnostic: DB access via Prisma, external service clients (email, Telegram, Turnstile), and pure logic. No `"use client"` code and no direct `NextRequest`/`NextResponse` handling here (that belongs in `src/app/api/`).

## Local Contracts

- `cache.ts` wraps Upstash Redis with an in-memory TTL fallback (`cacheGet`/`cacheSet`/`cacheDel`/`rateLimit`/`cacheSetNX`) — always invalidate **both** layers when mutating procedures or schedule data; a stale in-memory hit survives a Redis-only invalidation.
- `tenant.ts`'s `getTenantConfig()` caches the singleton `TenantConfig` row for 30s (`cache.ts`, key `tenant:config`) — it's read from the root `layout.tsx` on every page, so an uncached DB hit there is a site-wide cost under load (confirmed via load test: p99 ~9.5s at 20 concurrent connections before this fix, vs ~1.7s for an already-cached route). The DB-unavailable fallback (`catch` → `DEFAULT_CONFIG`) is deliberately never cached — caching it would mask a real outage for the TTL window. **Any route that writes `TenantConfig` must call `invalidateTenantConfigCache()` (also exported from `tenant.ts`) right after the write succeeds**, so admin settings changes apply immediately instead of waiting out the TTL — see the 6 call sites already doing this (`admin/settings/actions.ts`, `admin/settings/legal/actions.ts`, `api/admin/{notification,social,email,client-bot}-settings/route.ts`) as the pattern for any new one.
- `auth-guards.ts`'s `checkLoginGuards({ ip, email, turnstileToken })` gates the Credentials `authorize()` callback in `src/auth.ts`: a wide-sweep per-IP cap of 30 attempts/15min (`rate:login:<ip>`) plus a stricter per-account cap of 10 attempts/15min (`rate:login:acct:<normalizedEmail>`, the actual brute-force target) — both checked unconditionally, then `validateTurnstileForAPI(token, ip, { requireToken: false })`. It fails **open** only when Turnstile's own outbound `fetch` throws (`VERIFY_ERROR` — a Cloudflare/egress outage must never lock the salon out of its own admin panel); missing/invalid/expired/replayed tokens still fail closed. On `RATE_LIMITED`, `src/auth.ts` throws a `RateLimitedError` (a `CredentialsSignin` subclass, code `rate_limited`) instead of returning `null`, which `LoginForm.tsx` surfaces as a distinct "too many attempts" message rather than the generic invalid-credentials one. Deliberately a separate module from `src/auth.ts` (imports only `@/lib/cache` + `@/lib/turnstile`, no Prisma/next-auth) because `@/auth` is not importable under Vitest — this is what keeps the login guard unit-testable. `consent-service.ts`'s `getRequestIp()` takes a plain `Request` (not `NextRequest`) precisely so `authorize()`'s reconstructed `Request` can share it — there is exactly one IP-extraction convention in the repo.
- **Every `User.email` lookup used for authentication (login, forgot-password, register's duplicate check) must be case-insensitive**, via `` prisma.$queryRaw`SELECT id FROM User WHERE LOWER(email) = ${normalized}` `` — never a plain `findFirst({ where: { email } })` (2026-08-07 fix). `mode: 'insensitive'` isn't available on the SQLite/libSQL connector, so this can't be done through Prisma's normal query builder. Just lowercasing the *input* isn't sufficient either: `/api/auth/register` normalizes to lowercase before storing, but `createMaster` (`admin/masters/actions.ts`) and `scripts/create-admin.ts` do **not** — an account created through either of those can have a mixed-case stored email, and a login attempt that only lowercases its own input would silently fail to match it. This was a real production bug: a user could register, get "wrong password" on login and on every subsequent attempt after a password reset, purely from a casing mismatch between how the address was typed at registration vs. login — the password was never the problem. `src/auth.ts`'s `authorize()`, `api/auth/forgot-password/route.ts`, and `api/auth/register/route.ts`'s duplicate check all use this pattern now; give any new email-lookup call site the same treatment.
- `availability.ts` is the single source of truth for bookable slots — combines `Schedule`, `DateOverride`, and existing `Appointment` rows. Don't recompute availability logic elsewhere.
- `encryption.ts` is mandatory for any secret at rest (OAuth client secrets, SMTP password, `User.passwordEncrypted` for master password recovery) — never store or log a plaintext secret from `TenantConfig`. It **requires** `AUTH_SECRET` and throws at import if missing/empty (no insecure fallback key).
- `notifications/` (`index.ts` dispatcher + `internal.ts` + `email.ts` + `telegram.ts` + `client-telegram.ts` + `reminders.ts` + `sms/` + `templates.ts` + `template-store.ts`): public functions never throw — failures are caught and written to `NotificationLog`, not surfaced to the caller. Keep that contract when adding a new notification type. `internal.ts` holds the shared internals extracted to keep `index.ts` under 500 lines: `logNotification`, `formatDate`, `getTelegramRecipients()` (reads all `TelegramNotificationRecipient` rows), `broadcastTelegram(botToken, recipients, html)` (sends to every recipient, returns `{ anySuccess, lastError }`), `BookingActor` (`'client' | 'master' | 'admin'`), `actorLabel(actor, masterName?)` (client→`'Klient'`, admin→`'Administrator'`, master→named `` `Mistrz ${masterName}` `` or generic `'Mistrz'` if no name), the pure `buildBookingUpdateMessage(input)` (builds the `notifyBookingUpdate` Telegram body from a `previous`/`current` snapshot pair, rendering only the changed aspect(s), returning `null` when nothing changed), and `appointmentStartUtc(date, startTime)` — reconstructs an appointment's absolute UTC instant from its stored `date` (UTC midnight) + `startTime` ("HH:MM", Warsaw local wall-clock as written by `booking-service.ts`) via `fromZonedTime(..., SCHEDULE_TZ)` from `date-fns-tz`; **do not** rebuild that instant with a raw `` `${dateStr}T${startTime}:00.000Z` `` string (treats local time as UTC — was the pre-2026-08-23 reminder-window bug, off by the DST offset). Both are unit-tested in `tests/lib/notifications-internal.test.ts` with no Prisma mocking needed. Every admin/salon Telegram send (`notifyBookingConfirmation`, `notifyContactForm`, `notifyBookingCancellation`, `notifyBookingUpdate`) fetches recipients once per call and broadcasts to all of them (one `NotificationLog` summary row per event), replacing the old single `TenantConfig.notifAdminChatId`. `notifyBookingConfirmation(appointmentId, actor)`, `notifyBookingCancellation(appointment, actor)` (takes a pre-loaded snapshot — callers on hard-delete routes must fetch/pass it *before* deleting the row), and `notifyBookingUpdate(appointmentId, previous, actor)` all require a `BookingActor` (no default, so `tsc` catches any missed call site) and append a Polish "who changed it" line to their Telegram message only (never the email templates). `notifyBookingUpdate` self-fetches the NEW committed appointment state and diffs it against the caller-supplied `previous` snapshot (`{ date, startTime, serviceId, serviceName }`) to detect a service change and/or a date/time change independently — it renders only the changed aspect(s) and no-ops (sends nothing, logs nothing) if neither changed, so callers now fire it **unconditionally** after every committed update rather than gating on a caller-side diff; `NotificationLog.type` is `'BOOKING_UPDATE'`. It must be called AFTER the update/transaction is awaited (it reads current state fresh). Call sites fire all three fire-and-forget (`.catch(console.error)`), never awaited. `client-telegram.ts` sends the client-facing booking-reminder Telegram message via `TenantConfig.clientBotToken` on `NotificationLog.channel = 'telegram_client'` (distinct from the admin-salon `'telegram'` channel), gated by `clientBotEnabled` + `User.telegramChatId`; plain text (no HTML parse mode). As of 2026-08-23 it is **transport only** — `sendClientBookingReminder({ botToken, chatId, text })` takes a pre-rendered body (composed by `reminders.ts` from `NotificationTemplate`/`DEFAULT_REMINDER_BODIES.telegram` the same way the SMS body is composed) and no longer imports `botT()`/`telegram-bot/i18n.ts` or takes `lang`/`hours`/`labels`.
- `reminders.ts` holds `notifyBookingReminders()` — extracted out of `index.ts` (2026-08-23, behavior-preserving) because `index.ts` was already over the 500-line limit before SMS wiring; `index.ts` re-exports it (`export { notifyBookingReminders } from './reminders'`) so `src/app/api/cron/reminders/route.ts` needed zero changes. The 24h/2h reminder cron now sends client email + client-Telegram + client-SMS reminders (three independently-deduped channels via `NotificationLog.channel` — `email` / `telegram_client` / `sms`, each checked with its own `findFirst({ ..., status: 'sent' })` before sending); it still sends no admin/salon Telegram message. As of 2026-08-23 all three channels' bodies resolve from `NotificationTemplate` via the same mechanism: `getSmsSender(config)` + `loadReminderTemplates(channel)` (one call per enabled channel — `sms`/`email`/`telegram`, each gated on that channel actually being usable so a disabled channel costs zero queries) are built **once per cron run**, and a single shared `TemplateVars` object is built **once per appointment** (not rebuilt per channel) and passed to `renderTemplate(resolveReminderBody(templates, channel, type, lang), templateVars)` for each of the three sends.
- `sms/` (`index.ts` + `twilio.ts` + `smsapi.ts`) is the BYO SMS channel: two providers (Twilio, SMSAPI.pl) behind one closure-based sender, same `Promise<Error | null>`/never-throw contract as `client-telegram.ts`. `getSmsSender(config: SmsConfigSource)` decrypts credentials once and returns a sender closure, or `null` when disabled/unconfigured (`isSmsConfigured()`); `sendSms(to, text)` is a self-loading convenience wrapper used only by the admin test-send route (`api/admin/sms-settings/test`) — the cron path always uses `getSmsSender` directly to avoid re-decrypting per appointment. Both provider modules use native `fetch` with a 10s `AbortSignal.timeout` (a hung provider socket must not stall the rest of an hourly cron run) and never log/return a secret. `smsapi.ts` treats HTTP 200 with a JSON `{ error, message }` body as a failure — SMSAPI's `.do` endpoint does not use HTTP status codes for API errors, so checking `res.ok` alone would silently swallow every failure.
- `templates.ts` (pure — zero Prisma, zero React, unit-tested with no mocks) vs `template-store.ts` (Prisma-backed reads) split the reminder-body system the same way `discounts/` splits `shared.ts`/`eligibility.ts` from `server.ts`. `templates.ts` owns `renderTemplate()`/`validateTemplateBody()` (`{{placeholder}}` substitution — a known token is replaced, an unknown one is left literal so a typo stays visible, never silently blanked), `estimateSmsSegments()` (GSM-7 vs UCS-2 segment/cost estimate for the admin editor's live counter — SMS-only, never rendered on the email/Telegram tab), `REMINDER_CHANNELS`/`ReminderChannel` (`'sms' | 'email' | 'telegram'`) and `MAX_BODY_LENGTH: Record<ReminderChannel, number>` (`{ sms: 640, email: 2000, telegram: 2000 }` — the per-channel body cap, since the SMS-tuned 640 would reject a normal email body), `escapeHtml()` (HTML-escapes a rendered plain-text body for safe interpolation into the reminder email — lives here rather than in `email.ts` so it's covered by this no-mocks test file without dragging `nodemailer`/`sendEmail` into the test graph; applied AFTER `renderTemplate()` so it covers both the admin's template text and every substituted value in one pass), and `DEFAULT_REMINDER_BODIES` (`Record<ReminderChannel, Record<ReminderType, Record<Language, string>>>`, channel as the outermost key since that's the axis selected first in the admin UI and the axis `loadReminderTemplates()` partitions on — literal constants, not `src/locales/*.json` keys, because i18next would try to interpolate `{{clientName}}` itself; `scripts/i18n-check.mjs` only inspects `t()` call sites so this isn't an i18n-parity violation; the `telegram` defaults reproduce the pre-2026-08-23 `bot.reminder.heading*`/`bot.reminder.details` output verbatim so a salon that never opens the editor sees no change). `template-store.ts` owns `loadReminderTemplates(channel)` (one `findMany` against `NotificationTemplate`, keyed `` `${type}:${language}` ``, called once per enabled channel per cron run) and `resolveReminderBody(templates, channel, type, language)` (stored row → `DEFAULT_REMINDER_BODIES[channel]` → `pl` fallback). `NotificationTemplate` has no seeding/backfill — an absent row means "use the default"; saving an empty body from the admin editor deletes the row (see `prisma/AGENTS.md`).
- `validation/`: `client-validators.ts` has zero dependencies (safe for client bundles); `api-schemas.ts` (Zod) is server-only and is what route handlers should parse request bodies with. `client-validators.ts` validators return an i18n KEY in `ValidationResult.error` (e.g. `'validation.phoneTooShort'`), not display text — callers render it with `t(result.error)`, or `t(result.error, result.errorParams)` for keys with `{{...}}` interpolation (only `validateRequired`'s `fieldRequired` key needs `errorParams` today).
- `errors/apiErrorKey.ts` maps an API route's `{ code }` field to an `errors.*` i18n key (`apiErrorKey(code?) => 'errors.<code>' | 'errors.generic'`) — pure, no React, whitelist-based. Used to translate `{ error, code }` API responses at the React edge instead of displaying the raw (mixed-language) `error` text. The whitelist (`KNOWN_ERROR_CODES`) is exported so tests can assert every enumerated code maps correctly (`tests/lib/errors/apiErrorKey.test.ts`) — add new codes there, not just to `errors.*` in the locale files.
- `i18n-shared.ts` holds the pure language constants/helpers (`Language`, `SUPPORTED_LANGUAGES`, `DEFAULT_LANGUAGE`, `LANGUAGE_NAMES`, `isValidLanguage`, `localeFor(lang)` — BCP-47 `Intl` locale mapping) with **zero React/i18next dependency**. `i18n.ts` (client i18next singleton, `.use(initReactI18next)`) does `export * from './i18n-shared'` so its public API is unchanged; `i18n-server.ts` imports directly from `i18n-shared.ts`, never from `i18n.ts`. Do not move these constants back into `i18n.ts` or have `i18n-server.ts` import from it — `react-i18next`'s `initReactI18next` calls `React.createContext` at module-eval time, which breaks Next's "Collecting page data" build phase (a restricted React build without `createContext`) for any Server Component whose module graph reaches it.
- `i18n-server.ts` is server-only (imports `next/headers`) — `getServerT()` reads the `lang` cookie (mirrored by `src/contexts/LanguageContext.tsx`) and returns a fixed-language translator for Server Components/Actions that can't use `useTranslation()`. It uses its own `i18next.createInstance()` (core `i18next` only, no `react-i18next` plugin) for exactly this reason.
- `localized-content.ts` is the framework-free resolver for per-locale DB columns (`Service.name_pl/en/uk`, `MasterProfile.bio_pl/en/uk`, `TenantConfig.termsContent_pl/en/uk`, `TenantConfig.privacyContent_pl/en/uk`) — `resolveLocalized(field, lang)` picks `field[lang]`, falling back to `pl` then any non-empty variant; `parseEnabledLocales(json)` validates `TenantConfig.enabledLocales`. Client components resolve at render with `useCurrentLanguage()`; server components pass the full `{ pl, en, uk }` object down rather than pre-resolving.
- `markdown-lite.ts` is a pure, framework-free parser (`parseMarkdownLite(src) => MdNode[]`) for the fixed Markdown subset used by the admin-authored legal documents (`## `/`### ` headings, `- ` lists, blank-line paragraphs, inline `**bold**` — everything else stays literal text). It never emits HTML strings, only a plain node tree; `src/components/legal/MarkdownLite.tsx` maps that tree to React elements (`dangerouslySetInnerHTML` is never used). Do not add a markdown npm dependency for this — the subset is intentionally small and hand-parsed.
- `parseEnabledLocales` also gates the app-wide UI language switcher (not just content authoring): `src/app/layout.tsx` threads `TenantConfig.enabledLocales` through `Providers` → `src/contexts/LanguageContext.tsx`'s `LanguageProvider`, which parses it and exposes the result as `supportedLanguages`. `src/components/LanguageToggle.tsx` (the sole consumer, rendered at 8 sites incl. the admin top bar) hides entirely when only one locale is enabled. A stale `lang` cookie/localStorage pointing at a since-disabled locale is reconciled to `DEFAULT_LANGUAGE` client-side on mount (`router.refresh()` if it had to correct); `i18n-server.ts`'s `getServerLanguage()` intentionally stays a DB-free cookie reader and does not perform this check.
- `notifications/index.ts` resolves **client-facing** copy (`sendBookingConfirmationToClient`, `sendBookingReminderToClient`) via the persisted `Appointment.clientLanguage` (the client's UI language at booking time, sent by `BookingForm.tsx`/`useBookingSubmit.ts` to `POST /api/book` and validated there) — both the service name (via `resolveLocalized()`) AND the email template chrome (heading/greeting/field labels/subject/footer, via `email-i18n.ts`'s `emailT(lang)`, `emailNotif.*` locale keys). Until 2026-08-07 only the service name was localized — the surrounding template was hardcoded Polish regardless of `clientLanguage`, so e.g. an English-language booking got an English service name inside an otherwise all-Polish email; do not reintroduce that split by adding new client-facing template text as a raw string instead of an `emailNotif.*` key. **Admin/salon-facing** copy (`sendBookingConfirmationToAdmin`, `sendContactFormToAdmin`, and the Telegram message to the salon chat) always resolves at `DEFAULT_LANGUAGE`/stays hardcoded Polish — deliberate, since there is no single reliable "admin language" for a salon-wide notification. Do not unify the two. The client-facing Telegram reminder also localizes via `Appointment.clientLanguage`, consistent with the client email. As of 2026-08-23 the reminder **body** (email and Telegram both) no longer comes from `emailNotif.reminder.heading`/`.greeting` or `bot.reminder.*` (those five locale keys were deleted, replaced by the admin-editable `NotificationTemplate`/`DEFAULT_REMINDER_BODIES` system in `templates.ts`) — only the reminder email's chrome (subject line, `<html lang>`, brand header, footer) still comes from `emailNotif.reminder.subject`/`.whenTomorrow`/`.whenSoon`/`.footer`, and `client-telegram.ts` is now a pure transport with no i18n import at all (see its own bullet above). The **confirmation** email is unaffected and stays fully `emailNotif.confirmation.*`-driven, including the four labels (`serviceLabel`/`masterLabel`/`dateLabel`/`timeLabel`) the reminder used to share with it — do not restore the deleted reminder keys or assume the confirmation template changed.
- `utils/date-formatters.ts` formatters are locale-aware: `get*Formatter(locale = 'pl-PL')` factories plus `formatTimeRange`/`formatFullDateTime`/`formatDateTime(..., locale = 'pl-PL')`. The old `timeFormatter`/`fullDateFormatter`/`dateFormatter`/`shortDateFormatter`/`compactDateFormatter` consts still exist as pl-PL-bound instances for backward compatibility. `formatISODate` remains locale-independent. `utils/date-fns-locale.ts` exports `dateFnsLocale(lang)`, the `date-fns` `Locale`-object equivalent of `localeFor()` — used wherever calendar grids call `date-fns`'s `format()` instead of `Intl.DateTimeFormat` (admin calendar views).
- `admin-permissions.ts` is the only place that parses/grants the `clients`/`gdpr` permission JSON on `User.adminPermissions` — route handlers and admin pages call `getPermissionsForRole()`, they don't parse the JSON themselves.
- `content/pages-server.ts` exposes two content-page authorization primitives: `canManagePage(user, page)` (sync, row-based — authorizes the session against an existing row's real owner) and `authorizePageOwner(user, requested)` (async — authorizes a client-*requested* `PageOwner` for `createPage`/`reorderPages`, which have no row to derive a scope from; returns a freshly built scope or `null`, never trusts the caller's object). `PageOwner` itself lives in `content/pages-shared.ts`, not here, because client components carry it as a prop and that module must stay framework/Prisma-free.
- `content/photo-ids.ts` is pure/React-free/Prisma-free (client-safe like `content/pages-shared.ts`) and holds `derivePhotoIds()`/`reorderPhotosByIds()` — dnd-kit tile ids for the photo editors are derived from the persisted `string[]` on every render and never stored; `reorderPhotosByIds` returns its input unchanged on any id-list mismatch because an `undefined` slot would fail `z.array(z.string())` on save and make `parseBlockConfig` fall back to `defaultConfigFor()`, wiping the block's photos.
- `api/error-handler.ts` + `api/error-responses.ts` are the shared error contract for route handlers — see [../app/api/AGENTS.md](../app/api/AGENTS.md).
- `constants/brand.ts`'s `DEFAULT_BRAND_NAME` is the single source of truth for the unconfigured-tenant brand-name fallback (used by `tenant.ts`, `layout.tsx`, `Header.tsx`, `Footer.tsx`, the `auth/*` pages, `email.ts`, `notifications/index.ts`) — it has zero imports so it's safely usable from both Prisma-backed server code and client components; no file should hardcode its own literal fallback string.
- Files must stay under 500 lines — `consent-service.ts` (13KB), `booking-helpers.ts` (10KB), `notifications/index.ts` (~309 lines, shrunk 2026-08-23 by the `reminders.ts` extraction) are the largest; split further growth into new files rather than extending these.
- Guest phone ownership verification/matching uses full-E.164 comparison via `phonesMatchE164()` in `utils/phone-normalization.ts` (normalizes both sides, never last-9-digits suffix matching). `booking-helpers.ts` no longer holds the dead `verifyBookingAccess`/`matchesSearchCriteria` access helpers — they were unused in production and have been removed.
- `canModifyBooking()` in `booking-helpers.ts` is live (no longer orphaned) — the 24h-modification guard in `bookings/cancel`, `bookings/update-time`, and `bookings/update-procedure` route handlers all call it instead of duplicating the hours-until-appointment math. It denies (`canModify: false`) for invalid/NaN dates.
- `discounts/` splits three ways: `shared.ts` (Prisma-free, React-free — types, `normalizeDiscountCode()`, window JSON parse/serialize, `applyPercent()`, `resolveAppointmentPrice()`, `discountPercentFromSnapshot()`; safe for client bundles), `eligibility.ts` (pure predicates — `isDiscountEligible()`, `pickBestDiscount()`, `explainCode()`, no Prisma/I-O, 100% unit-testable), and `server.ts` (Prisma-backed — `canManageDiscount()`/`authorizeDiscountScope()` authorization pair mirroring `content/pages-server.ts`, `listMasterOfferedServiceIds()`, `evaluateDiscount()`, `resnapshotAppointmentPrice()`). `evaluateDiscount()` is the **single source of truth** for every price shown or charged — the preview route, `/api/procedures`, `createBooking()`, and the Telegram bot (in-process, never via HTTP self-call) all call through it. Highest `percent` wins and discounts never stack (`pickBestDiscount()`). Evaluation has three stages (`'catalog' | 'slot' | 'final'`) gating which constraints apply (see `EligibilityContext`). `resnapshotAppointmentPrice()` is called by every route that can change an appointment's service (AD-7) — it re-prices at the new service, clears `discountId`, and deletes the redemption row. `hhmmToMinutes()` in `shared.ts` deliberately duplicates `t2m` from `schedule-utils.ts`, which cannot be imported into a client-safe module because it pulls in Prisma at module scope.
- `og-image.ts` holds the OG-card helpers (`OG_SIZE`, `safeColor`, `truncateBrandName`, `brandFontSize`, `resolveUploadPath`, `loadOgLogo`); every function is total (returns a fallback/`null`, never throws) because the module is reachable from every page's metadata; `sharp` is imported **lazily inside** `loadOgLogo` on purpose — a broken native binding must cost only the preview card. It normalises uploads to PNG because satori rejects WebP/AVIF and unparseable SVGs, and because `TenantConfig.logoWidth/logoHeight` are header display dims, not the file's real aspect ratio. `/uploads/` paths are regex-guarded against traversal.
- `telegram-bot/`: the client booking wizard gained a `'PROMO'` step (`WizardStep`), reachable only as an optional affordance from the existing `CONFIRM` step (`handlers/promo.ts`). `handlers/promo.ts` **must stay registered before `handlers/contact.ts`** in `bot.ts` — `contact.ts`'s `message:text` listener never calls `next()` when it doesn't own the current step, which halts grammy's middleware chain for any later-registered `message:text` listener; `promo.ts`'s own listener always calls `next()` when it doesn't own `'PROMO'`, so registration order is load-bearing and invisible to `tsc`/`lint`/`build`.
