# AGENTS.md — src/app/admin

## Purpose

Salon management dashboard. Two role-scoped surfaces share this tree: full management for `ADMIN`/`SUPERADMIN` (masters, services, all schedules, all appointments, database/GDPR tools, tenant settings), and a restricted self-service view for `MASTER` under `admin/master/` (own schedule, own overrides, own appointments).

## Ownership

Dashboard page composition and role-gated views. Data mutations go through `src/app/api/admin/**` and `src/app/api/master/**`; this folder only renders and calls those endpoints.

## Local Contracts

- Every page here is a Server Component that calls `auth()` and redirects to `/auth/login` if `session.user.role` doesn't match what the page requires — `admin/master/*` pages check for `"MASTER"` specifically, top-level `admin/*` pages check for `"ADMIN"`/`"SUPERADMIN"`. `src/middleware.ts` provides a first-pass guard, but pages must not skip their own check.
- Fine-grained ADMIN permissions (client data view/edit/delete, GDPR view/withdraw/erase) come from `src/lib/admin-permissions.ts` — gate UI affordances (buttons, tabs) on the parsed permission object, not on role alone.
- `settings/` (email, notifications, social, OAuth/SMTP credentials) writes to the single `TenantConfig` row — encrypted fields (OAuth secrets, SMTP password) must pass through `src/lib/encryption.ts` before persisting; never render decrypted secrets back into the page.
- `masters/`: master passwords are stored encrypted (`User.passwordEncrypted`, via `src/lib/encryption.ts`) and can be revealed on explicit admin request through the `getMasterPassword` server action (`masters/actions.ts`), which enforces its own ADMIN/SUPERADMIN check independent of the page guard. This is an intentional, scoped exception to the "never render decrypted secrets back into the page" rule above, which applies to `settings/`.
- `database/gdpr/` triggers erasure/withdrawal flows — these are irreversible for the affected user; confirm-before-submit UX must not be removed (see the `useConfirm()` Work Guidance bullet below — this is the mechanism, not just a UX note).
- Content pages have **three** admin surfaces sharing one component set (`PageListClient`/`PageFormSheet`/`PageBlocksEditor`) and one action set (`src/app/admin/pages/actions.ts` + `block-actions.ts`): `pages/` (global), `master/pages/` (MASTER self-service), and `masters/[masterId]/pages/` (ADMIN/SUPERADMIN acting on a specific master, entered via the "Manage pages" icon on a masters row — navigation to a different resource, not a second edit entry point per C-2). Row-targeted actions (update/delete/toggle/block actions) authorize the session against the row's own owner via `canManagePage`; `createPage`/`reorderPages` (no row to derive a scope from) take an explicit `PageOwner` requested by the client and authorized server-side by `authorizePageOwner`. ADMIN/SUPERADMIN may manage global pages **and** any master's pages; MASTER only their own.
- Discounts have **two** surfaces (`discounts/` global, `master/discounts/` self-service, unlike content pages there is deliberately **no** admin-on-behalf third surface) sharing one component set (`src/components/admin/discounts/`) and one action set (`src/app/admin/discounts/actions.ts`). `createDiscount` takes a required `DiscountOwner` as its leading parameter, authorized server-side by `authorizeDiscountScope` (a forgotten/wrong argument is a `tsc` error, never a silent global write); row-targeted actions (`updateDiscount`/`deleteDiscount`/`toggleDiscountActive`) authorize against the row's own owner via `canManageDiscount` and never accept an owner from the client — `updateDiscount` never changes `masterId`. `ViewAppointmentModal.tsx` (admin/master calendar) shows the applied discount beneath the price row (label + percent, percent derived from the price snapshot via `discountPercentFromSnapshot()` when the `Discount` row has since been deleted) — the only calendar surface that does; client-facing screens (profile, booking-management) deliberately show no discount badge.

## Work Guidance

- **i18n**: every screen here renders in pl/uk/en via the `admin.*` locale namespace (`src/locales/{pl,en,uk}.json`, sub-grouped `admin.nav.*`/`admin.dashboard.*`/`admin.services.*`/`admin.masters.*`/`admin.admins.*`/`admin.database.*`/`admin.gdpr.*`/`admin.settings.*`/`admin.calendar.*`/`admin.appointments.*`/`admin.common.*`; reuse `common.*`/`profile.status*`/`form.*` where the concept already exists there instead of duplicating into `admin.*`). `"use client"` components (the majority) call `useTranslation()` directly. Server Components/`actions.ts` server actions call `getServerT()` from `src/lib/i18n-server.ts` — never import translation helpers from `src/lib/i18n.ts` in server-only code (see that file's AGENTS.md for why). Zod validation messages in `actions.ts` come from a `build<X>Schema(t)` factory called with `getServerT()`'s result, not a module-scope schema constant. Date/time text uses `localeFor()` (`Intl`) or `dateFnsLocale()` (`date-fns`) keyed off the active language — never a hardcoded weekday/month array or unlocalized `format()`/`toLocaleDateString()` call. Admin fetch consumers map a `{ code }` API response through `t(apiErrorKey(code))` (`src/lib/errors/apiErrorKey.ts`), never render a raw `error` string.
- Reuse `AdminSidebar` (`src/components/admin/AdminSidebar.tsx`) for navigation; don't hand-build a second sidebar for a new section. Nav items (`labelKey`/href/icon/role) live in `src/components/admin/adminNavItems.ts` — add a new route there (as an `admin.nav.*` key, not a literal string) and both the sidebar and `AdminTopBar`'s page title pick it up automatically; don't hardcode a title in the page itself.
- `src/app/admin/layout.tsx` renders `AdminSidebar` + `AdminTopBar` around `{children}`; the sidebar collapses (240px⇄72px) via its own local state, `AdminTopBar` needs no props and no wiring from individual pages.
- **Mobile breakpoint (`lg`, 1024px):** the one structural mobile/desktop divide across the admin dashboard — no custom Tailwind screen, just the default `lg`. At/above `lg`, everything is the pre-existing desktop layout (240px⇄72px sidebar, `w-[calc(100vw-240px)]` main-container lock). Below `lg`: `AdminSidebar.tsx`'s persistent `<aside>` is `hidden lg:flex` (fully absent, not just collapsed) and replaced by an off-canvas `Sheet` drawer (`side="left"`), and `admin/layout.tsx`'s `<main>` inner container goes `w-full lg:w-[calc(100vw-240px)]` (full-width below `lg`, since the sidebar takes zero layout space there). The drawer opens via `AdminTopBar.tsx`'s hamburger button (`lg:hidden`) dispatching a `document.dispatchEvent(new CustomEvent('admin-drawer-open'))`, mirroring the existing `settings-dirty` event bridge below — listened for locally inside `AdminSidebar.tsx` (`useState`, no React context). The drawer auto-closes on route change (`usePathname` effect). The sidebar's nav body (links, back-to-site, settings-save button, user/theme/sign-out footer) is a co-located `SidebarNav` sub-component taking `expanded: boolean`, shared between the persistent aside (`expanded={open}`) and the drawer (`expanded={true}`, always full nav, never icon-only).
- Keep page files under 500 lines — split list/detail/form pieces into `src/components/admin/` or co-located client components as this folder already does (e.g. `admin/master/AppointmentsList.tsx`).
- Dashboard stat cards use `src/components/admin/StatCard.tsx` (`tone: "primary" | "secondary" | "tertiary" | "surface-high"`, mapped to the raw `--md-*-container` vars, not the tenant-customizable `bg-primary`/`bg-accent`/etc). Appointment status pills use the shared `src/components/admin/AppointmentStatusBadge.tsx` everywhere a status is rendered (`admin/page.tsx`'s `TodaysAppointmentsTable` and `admin/master/AppointmentsList.tsx`) — don't hand-roll a new status→color mapping.
- Calendar views (`admin/master/calendar/{ModernCalendar,WeekView,DayView,MonthView}.tsx`) follow the same raw `--md-*-container` convention for hardcoded red/green status pills (`bg-[var(--md-error-container)] text-[var(--md-on-error-container)]`, success equivalent) instead of Tailwind's `red-*`/`green-*` scale. Appointment/event blocks use a soft tonal tint (`color+"26"` alpha) with `text-foreground` and a `3px` left accent border in the master's color, not a solid fill with forced white text — this stays legible for any admin-picked hex, including light/pastel colors. `.custom-scrollbar` (defined in `src/styles/globals.css`) is the shared thin-scrollbar utility for calendar scroll areas and dropdown panels. `admin/master/calendar/` also holds `CalendarToolbar.tsx` (the toolbar, split out of `ModernCalendar.tsx`), `MasterSelectDropdown.tsx` (the admin master-filter `createPortal` dropdown), `calendar-utils.ts` (`groupOverlappingAppointments`/`pluralize`/`parseTime`, shared by Month/Week/Day — import from here, don't re-declare), `WeekDayEditPopover.tsx` (WeekView's per-day shift editor popover), and `AppointmentTimeSelect.tsx` (the `AppointmentModal` start-time picker: fetches real free slots from `${apiPrefix}/availability/slots`, keyed on master/date/duration/exclude-id, instead of allowing an arbitrary time) — all pure extractions kept under the 500-line limit; `ModernCalendar.tsx` itself is now a lean shell (state, data fetch, view switch, modals).
- The manual appointment create/edit form (`AppointmentModal.tsx`) only offers real availability: `AppointmentTimeSelect.tsx` calls `GET /api/master/availability/slots` or `GET /api/admin/calendar/availability/slots` (both thin wrappers over `getDaySlots()` in `src/lib/availability.ts`), passing `excludeAppointmentId` in edit mode so the appointment's own current slot stays selectable. `AppointmentDateSelect.tsx` is the date-field counterpart: it fetches `${apiPrefix}/availability/days` (thin wrappers over `getAvailableDays()`) for the currently visible month and greys out the selected master's day-off dates via `DatePickerDropdown`'s optional `disabledDates`/`onVisibleMonthChange` props — no master selected (admin view) leaves every day enabled, and edit mode never disables the appointment's own current date (`excludeOriginalDate`, since `getAvailableDays()` has no exclude-self option). Do not reintroduce a plain `TimePickerDropdown` (unrestricted time entry) here — that component remains for other calendar consumers (WeekView/DayView/BulkSettingsModal/EditAppointmentModal) that don't need availability-awareness.
- The service dropdown in `AppointmentModal.tsx` is master-scoped, via `AppointmentServiceSelect.tsx` (a small presentational Select + custom-name-input extraction, mirroring `AppointmentTimeSelect`/`AppointmentDateSelect`): a services-fetch effect keyed on `[apiPrefix, isAdminView, formMasterId]` refetches `${apiPrefix}/services?masterId=...`, and a selection is silently reset to `"custom"` when it's no longer offered by the (possibly newly chosen) master — the edit-mode current service is never cleared just because it opens with a service outside the master's `MasterService` join, only on an actual reassignment. An ADMIN can reassign the master while editing (the master `<Select>` is only disabled when `mode === "edit" && !isAdminView`, i.e. never inside the already-`isAdminView`-gated block); a master's own calendar still has no master field. CREATE-mode series carry a per-entry service (`Entry.serviceId`/`customServiceName`, one `AppointmentServiceSelect` per date row) instead of one shared service — selecting a real service auto-fills only that entry's duration; EDIT mode keeps the single shared service field and the PUT routes untouched.
- **Calendar mobile (`isMobile` from `useIsMobile()`, read in `ModernCalendar.tsx` after its `isMounted` gate, passed down as a prop):** full view parity below `lg` — Month/Week/Day all stay selectable, never forced to a single view. `CalendarToolbar.tsx` branches internally: desktop keeps its two-row toolbar verbatim; mobile renders a compact top row (prev/next/today + period label + a controls icon button) plus an always-visible Month/Week/Day segmented switcher, with the step selector/Edit Schedule/Bulk Settings/`MasterSelectDropdown` relocated into a bottom `Sheet` (`side="bottom"`) opened by the controls button. `MonthView.tsx` renders a compact mobile cell (date number + an appointment-count badge + day-off shading) and hides the in-cell shift-editor/off-shift affordances on mobile (schedule editing there happens in Day/Week or Bulk Settings) — tapping any day navigates to Day view. `WeekView.tsx` keeps the true 7-day grid on mobile but gives each day column a fixed `110px` width inside a horizontally-scrollable region; the day-name header row and the grid body are two separate scroll containers kept in sync via a small `scrollLeft` mirror effect (`headerScrollRef`/`bodyScrollRef`), with the hours gutter as a non-scrolling sibling column in each — desktop's `grid-cols-7` path is untouched. `DayView.tsx` only got Tailwind-class-only narrow-width polish (no JS branch).
- Every `page.tsx` that's an `async` Server Component gets a sibling `loading.tsx` (Next.js wraps the segment in `<Suspense>` automatically) composing the shared skeletons in `src/components/admin/skeletons/` (`StatCardsSkeleton`, `TableSkeleton` with a `rows` prop, `FormSkeleton`), themselves built on the `src/components/ui/skeleton.tsx` primitive — pick the composition that matches the route's content shape (dashboard: stat cards + table; list/table pages: table; settings pages: form) and wrap it in the same outer container classes as the real page so content doesn't jump on hydration. Skip `loading.tsx` for pages that aren't `async` Server Components (`admin/calendar/page.tsx` is `"use client"` with its own spinner; `settings/email`, `settings/social` are synchronous) — it wouldn't do anything for them.
- Some `settings/` forms (main `SettingsForm.tsx`, `notifications/NotificationSettingsForm.tsx`) drive the shared sidebar "Save Settings" button instead of (or alongside) their own inline button: `<form id="settings-form">` + a `useEffect` dispatching `new CustomEvent('settings-dirty', { detail: { isDirty: formState.isDirty } })`, consumed by `AdminSidebar.tsx`'s listener and its `form="settings-form"` button. `form.reset(values)` after save clears the dirty state. Others (`email/`, `social/`, `legal/`) are self-contained with only their own inline save — check which pattern a form uses before touching it; the `id`/event name/`detail` shape and the reset call are invisible to `tsc`/`lint`/`build` if broken. `legal/actions.ts`'s `saveLegalContent` re-checks the ADMIN/SUPERADMIN role itself, independent of the page guard — legally significant content, the same exception already carved out for `getMasterPassword` above; `saveSettings` (main settings) has no such check, which is pre-existing and untouched.
- List/table surfaces (Services, Masters, Admins, Database's Clients/GDPR tables, DB Browser) share one chrome convention, canonical in `admin/services/ServicesClient.tsx`: table container `rounded-[20px] border border-border bg-card shadow-sm overflow-hidden`, `<thead className="bg-muted/50 text-muted-foreground">` with uppercase micro-label `<th>`s (`text-[11px] font-medium uppercase tracking-wider`), `<tbody className="divide-y divide-border">` + `<tr className="hover:bg-muted/40 transition-colors">` (no zebra striping). Binary-state pills use `Badge variant="success"/"muted"/"warning"` (e.g. Masters visibility, Database client type, GDPR status, DB Browser's SUPERADMIN-only pill), not raw colored `<span>`s.
- **Table→card below `lg`:** every `<table>`-based surface (Services, Master Services, Database's Clients/GDPR tables, dashboard `TodaysAppointmentsTable`) wraps its `<table>` in `hidden lg:block` and adds a `lg:hidden` list mapping the same row data to `src/components/admin/DataCard.tsx` (1–2 prominent fields + the rest as secondary `label`/`value` pairs; row actions in the `actions` slot; `Badge` pills render the same inside cards). Per-row edit affordances that open a `Sheet`/`Dialog` must use ONE shared instance controlled by an `editTarget`/`editOpen` state pair with plain trigger buttons in both layouts — do NOT duplicate a per-row `Sheet` into both the table and the card list, since both would mount and pop open together off the same shared state (`ServicesClient.tsx`/`MasterServicesClient.tsx` show the pattern). **`db-browser/DbBrowserClient.tsx` is the one exception** — SUPERADMIN-only diagnostic tooling with arbitrary/many dynamic columns stays a horizontal-scroll `<table>` (`overflow-x-auto custom-scrollbar` inner wrapper + a `min-w` on the table, outer rounded chrome unchanged) rather than cards. Card-based lists that were already flex cards (`MastersClient.tsx`, `AdminsClient.tsx`) just need a `min-w-0`/`truncate` audit on their row text, not a table→card conversion.
- `settings/` sub-pages (main, `email/`, `social/`, `notifications/`) share one card+header-bar chrome via `SettingsSection` (`src/app/admin/settings/FormFields.tsx`: `title`/`description?`/`action?`/`children`, no icon slot). Forms living outside `src/app/admin/settings/` (e.g. `src/components/admin/EmailSettingsForm.tsx`, `SocialSettingsForm.tsx`) import it directly from that path rather than duplicating the markup or promoting it — an accepted, deliberate `components → app` import-direction exception. Each settings page's own header is an eyebrow (`text-xs font-medium uppercase tracking-wider text-primary`, copy: "Configuration") + muted subtitle, no `<h1>` — the topbar (`adminNavItems.ts`) already supplies the page title.
- **Per-locale content authoring** (`Service.name_*`, `MasterProfile.bio_*`, `TenantConfig.termsContent_*`/`privacyContent_*`): `services/ServiceForm.tsx`, `master/services/MasterServiceForm.tsx`, `masters/MasterForm.tsx`, and `settings/legal/LegalSettingsForm.tsx` all render `src/components/admin/LocalizedFieldInput.tsx` instead of a plain input, gated by the tenant's `TenantConfig.enabledLocales` (`settings/LanguagesSection.tsx` is the toggle UI, `pl` always enabled). Each server page fetches `enabledLocales` via `getTenantConfig()` + `parseEnabledLocales()` (`src/lib/localized-content.ts`) and threads it down through the client list component to the form. Server actions/API routes only write a `name_en`/`name_uk`/`bio_en`/`bio_uk`/`termsContent_en`/`termsContent_uk`/`privacyContent_en`/`privacyContent_uk` column when that field is present in the submission (locale currently enabled) — an absent field leaves the existing DB value untouched rather than nulling it, so temporarily disabling a locale never destroys a saved translation. Unlike `name_pl` (NOT NULL), `termsContent_pl`/`privacyContent_pl` are nullable and use this same absent-vs-empty write rule — no locale, including `pl`, is privileged. List/table displays (`ServicesClient.tsx`, `MasterServicesClient.tsx`, `MastersClient.tsx`) resolve the viewer-language value at render via `useCurrentLanguage()` + `resolveLocalized()`; the public `/terms`/`/privacy` pages do the same via `src/components/legal/LegalDocumentView.tsx`.
- `ModernCalendar`'s `availableSlotColor`/`dayOffColor` props (and the matching `TenantConfig.availableSlotColor`/`dayOffColor` DB fields) must stay **literal hex strings everywhere they're read, passed, or defaulted** — never a CSS `var(...)` reference. Every consumer does `color + "NN"`-style string concatenation for alpha, which silently produces invalid CSS given a `var()` string (browser-only failure, invisible to `tsc`/`lint`/`build`). When changing the default hex, every call site/fallback must be updated in lockstep (`admin/calendar/page.tsx`, `admin/master/schedule/page.tsx`, `admin/settings/page.tsx`'s config-seeding) — a mismatched literal at any one of them silently overrides the others.

- Destructive actions use `await useConfirm()(t('…'))` (`src/components/ConfirmDialogProvider.tsx`) and error paths use `toast.error(t('…'))` (sonner) — native `alert`/`confirm`/`prompt` are banned app-wide by the `no-alert` ESLint rule.
