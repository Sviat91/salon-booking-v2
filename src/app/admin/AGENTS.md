# AGENTS.md — src/app/admin

## Purpose

Salon management dashboard. Two role-scoped surfaces share this tree: full management for `ADMIN`/`SUPERADMIN` (masters, services, all schedules, all appointments, database/GDPR tools, tenant settings), and a restricted self-service view for `MASTER` under `admin/master/` (own schedule, own overrides, own appointments).

## Ownership

Dashboard page composition and role-gated views. Data mutations go through `src/app/api/admin/**` and `src/app/api/master/**`; this folder only renders and calls those endpoints.

## Local Contracts

- Every page here is a Server Component that calls `auth()` and redirects to `/auth/login` if `session.user.role` doesn't match what the page requires — `admin/master/*` pages check for `"MASTER"` specifically, top-level `admin/*` pages check for `"ADMIN"`/`"SUPERADMIN"`. `src/middleware.ts` provides a first-pass guard, but pages must not skip their own check.
- Fine-grained ADMIN permissions (client data view/edit/delete, GDPR view/withdraw/erase) come from `src/lib/admin-permissions.ts` — gate UI affordances (buttons, tabs) on the parsed permission object, not on role alone.
- `settings/` (email, notifications, social, OAuth/SMTP credentials) writes to the single `TenantConfig` row — encrypted fields (OAuth secrets, SMTP password) must pass through `src/lib/encryption.ts` before persisting; never render decrypted secrets back into the page.
- `masters/`: master passwords are stored encrypted (`User.passwordEncrypted`, via `src/lib/encryption.ts`) and can be revealed on explicit admin request through the `getMasterPassword` server action (`masters/actions.ts`), which enforces its own ADMIN/SUPERADMIN check independent of the page guard. This is an intentional, scoped exception to the "never render decrypted secrets back into the page" rule above, which applies to `settings/`.
- `database/gdpr/` triggers erasure/withdrawal flows — these are irreversible for the affected user; confirm-before-submit UX must not be removed.

## Work Guidance

- **i18n**: every screen here renders in pl/uk/en via the `admin.*` locale namespace (`src/locales/{pl,en,uk}.json`, sub-grouped `admin.nav.*`/`admin.dashboard.*`/`admin.services.*`/`admin.masters.*`/`admin.admins.*`/`admin.database.*`/`admin.gdpr.*`/`admin.settings.*`/`admin.calendar.*`/`admin.appointments.*`/`admin.common.*`; reuse `common.*`/`profile.status*`/`form.*` where the concept already exists there instead of duplicating into `admin.*`). `"use client"` components (the majority) call `useTranslation()` directly. Server Components/`actions.ts` server actions call `getServerT()` from `src/lib/i18n-server.ts` — never import translation helpers from `src/lib/i18n.ts` in server-only code (see that file's AGENTS.md for why). Zod validation messages in `actions.ts` come from a `build<X>Schema(t)` factory called with `getServerT()`'s result, not a module-scope schema constant. Date/time text uses `localeFor()` (`Intl`) or `dateFnsLocale()` (`date-fns`) keyed off the active language — never a hardcoded weekday/month array or unlocalized `format()`/`toLocaleDateString()` call. Admin fetch consumers map a `{ code }` API response through `t(apiErrorKey(code))` (`src/lib/errors/apiErrorKey.ts`), never render a raw `error` string.
- Reuse `AdminSidebar` (`src/components/admin/AdminSidebar.tsx`) for navigation; don't hand-build a second sidebar for a new section. Nav items (`labelKey`/href/icon/role) live in `src/components/admin/adminNavItems.ts` — add a new route there (as an `admin.nav.*` key, not a literal string) and both the sidebar and `AdminTopBar`'s page title pick it up automatically; don't hardcode a title in the page itself.
- `src/app/admin/layout.tsx` renders `AdminSidebar` + `AdminTopBar` around `{children}`; the sidebar collapses (240px⇄72px) via its own local state, `AdminTopBar` needs no props and no wiring from individual pages.
- Keep page files under 500 lines — split list/detail/form pieces into `src/components/admin/` or co-located client components as this folder already does (e.g. `admin/master/AppointmentsList.tsx`).
- Dashboard stat cards use `src/components/admin/StatCard.tsx` (`tone: "primary" | "secondary" | "tertiary" | "surface-high"`, mapped to the raw `--md-*-container` vars, not the tenant-customizable `bg-primary`/`bg-accent`/etc). Appointment status pills use the shared `src/components/admin/AppointmentStatusBadge.tsx` everywhere a status is rendered (`admin/page.tsx`'s `TodaysAppointmentsTable` and `admin/master/AppointmentsList.tsx`) — don't hand-roll a new status→color mapping.
- Calendar views (`admin/master/calendar/{ModernCalendar,WeekView,DayView,MonthView}.tsx`) follow the same raw `--md-*-container` convention for hardcoded red/green status pills (`bg-[var(--md-error-container)] text-[var(--md-on-error-container)]`, success equivalent) instead of Tailwind's `red-*`/`green-*` scale. Appointment/event blocks use a soft tonal tint (`color+"26"` alpha) with `text-foreground` and a `3px` left accent border in the master's color, not a solid fill with forced white text — this stays legible for any admin-picked hex, including light/pastel colors. `.custom-scrollbar` (defined in `src/styles/globals.css`) is the shared thin-scrollbar utility for calendar scroll areas and dropdown panels.
- Some `settings/` forms (main `SettingsForm.tsx`, `notifications/NotificationSettingsForm.tsx`) drive the shared sidebar "Save Settings" button instead of (or alongside) their own inline button: `<form id="settings-form">` + a `useEffect` dispatching `new CustomEvent('settings-dirty', { detail: { isDirty: formState.isDirty } })`, consumed by `AdminSidebar.tsx`'s listener and its `form="settings-form"` button. `form.reset(values)` after save clears the dirty state. Others (`email/`, `social/`) are self-contained with only their own inline save — check which pattern a form uses before touching it; the `id`/event name/`detail` shape and the reset call are invisible to `tsc`/`lint`/`build` if broken.
- List/table surfaces (Services, Masters, Admins, Database's Clients/GDPR tables, DB Browser) share one chrome convention, canonical in `admin/services/ServicesClient.tsx`: table container `rounded-[20px] border border-border bg-card shadow-sm overflow-hidden`, `<thead className="bg-muted/50 text-muted-foreground">` with uppercase micro-label `<th>`s (`text-[11px] font-medium uppercase tracking-wider`), `<tbody className="divide-y divide-border">` + `<tr className="hover:bg-muted/40 transition-colors">` (no zebra striping). Binary-state pills use `Badge variant="success"/"muted"/"warning"` (e.g. Masters visibility, Database client type, GDPR status, DB Browser's SUPERADMIN-only pill), not raw colored `<span>`s.
- `settings/` sub-pages (main, `email/`, `social/`, `notifications/`) share one card+header-bar chrome via `SettingsSection` (`src/app/admin/settings/FormFields.tsx`: `title`/`description?`/`action?`/`children`, no icon slot). Forms living outside `src/app/admin/settings/` (e.g. `src/components/admin/EmailSettingsForm.tsx`, `SocialSettingsForm.tsx`) import it directly from that path rather than duplicating the markup or promoting it — an accepted, deliberate `components → app` import-direction exception. Each settings page's own header is an eyebrow (`text-xs font-medium uppercase tracking-wider text-primary`, copy: "Configuration") + muted subtitle, no `<h1>` — the topbar (`adminNavItems.ts`) already supplies the page title.
- `ModernCalendar`'s `availableSlotColor`/`dayOffColor` props (and the matching `TenantConfig.availableSlotColor`/`dayOffColor` DB fields) must stay **literal hex strings everywhere they're read, passed, or defaulted** — never a CSS `var(...)` reference. Every consumer does `color + "NN"`-style string concatenation for alpha, which silently produces invalid CSS given a `var()` string (browser-only failure, invisible to `tsc`/`lint`/`build`). When changing the default hex, every call site/fallback must be updated in lockstep (`admin/calendar/page.tsx`, `admin/master/schedule/page.tsx`, `admin/settings/page.tsx`'s config-seeding) — a mismatched literal at any one of them silently overrides the others.
