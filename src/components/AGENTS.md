# AGENTS.md — src/components

## Purpose

Shared React components. `ui/` holds shadcn/ui primitives (Radix-based). Domain folders (`admin/`, `auth/`, `home/`, `profile/`, `reviews/`, `layout/`, `providers/`) hold feature-specific components. Top-level `.tsx` files are booking-flow components used directly by `src/app/[masterId]` and the landing page.

## Ownership

Presentation and client-side interaction only. Data fetching goes through React Query hooks; server calls go through `src/lib/api/` or route handlers — components don't embed business logic that belongs in `src/lib/`.

## Local Contracts

- `ui/` components follow shadcn/ui conventions (CVA variants, Radix primitives, `cn()` from `src/lib/utils.ts`) — when adding a new primitive, match the existing pattern (e.g. `button.tsx`) rather than hand-rolling styles.
- `ui/input.tsx` (and any Base-UI-derived primitive written React-19-style) is **not** `forwardRef`-wrapped while the project is on React 18, so a ref passed to it is silently dropped — bind it with `Controller`/`FormField`, not `register()` (2026-08-07: `register()`'s ref never attaching meant RHF read `undefined` off every keystroke in `notifications/TelegramRecipientsField.tsx`). Do not "fix" this by wrapping it in `forwardRef` without auditing every form — that changes `_f.ref` for every existing Controller-bound field app-wide.
- `ui/PhoneInput.tsx` (10 call sites: `BookingForm.tsx`, `BookingAuthDetailsCard.tsx`, `RegisterForm.tsx`, `profile/edit`, `LinkBookingsCard.tsx`, `DataExportModal.tsx`/`DataErasureModal.tsx`/`ConsentWithdrawalModal.tsx`, `booking-management/{SearchPanel,ContactMasterPanel}.tsx`) is a controlled component with two-way sync to its `value`/`onChange` props via a pair of `useEffect`s — one parses an external `value` into internal state (`selectedCountry`/`phoneNumber`/`customCountryCode`), the other notifies the parent when that internal state changes. A `skipNotifyRef` guard (2026-08-07 fix) prevents the second effect from re-notifying the parent with a truncated value when it fires in the same commit as the first effect but reads pre-update state — without it, mounting the component fresh with an already non-empty `value` (e.g. a booking form's phone field surviving a parent remount) caused a rapid empty/filled oscillation: the stale read produced a country-code-only value, which got treated as a real edit, sent back up as the new `value`, re-parsed to empty, and repeated. Do not remove `skipNotifyRef` without re-deriving this race by hand — it's not a leftover, it's load-bearing.
- `ui/skeleton.tsx` is the shared loading-placeholder primitive (`animate-pulse rounded-md bg-muted` div). `admin/skeletons/` composes it into route-shaped patterns (`StatCardsSkeleton`, `TableSkeleton`, `FormSkeleton`) consumed by `admin/**/loading.tsx` files — see [../app/admin/AGENTS.md](../app/admin/AGENTS.md) for the `loading.tsx` convention. Reuse these composed patterns instead of hand-building a new one per route.
- `ui/` primitives are `"use client"` files. A Server Component may render them as JSX (`<Button>`, `<DialogPrimitive.Close render={<Button/>}>` — the base-ui polymorphic pattern already used in `dialog.tsx`/`sheet.tsx`), but must NOT directly call a plain function they export (e.g. `buttonVariants()`) — that throws `TypeError: ... is not a function` at request time only, since the client-boundary bundling replaces the export with a reference that isn't invocable on the server. This doesn't surface in `next build` (dynamic routes aren't rendered at build time) or in a read-only code review — it only shows up on an actual request. If a Server Component needs a button-styled link, use `<Button variant="..." render={<Link href="..." />}>`, not `className={buttonVariants(...)}`.
- M3 design tokens live in `src/styles/m3-tokens.css` — component styling should reference CSS custom properties from there, not hardcode colors/spacing that duplicate a token.
- Most UI should use the tenant-customizable semantic layer (`bg-primary`/`bg-accent`/`bg-muted`/etc in `src/styles/globals.css`, backed by `TenantConfig`). A few decorative/status colors intentionally bypass this and reference raw `--md-*` vars directly (e.g. `badge.tsx`'s `success`/`warning`/`destructive` variants, `admin/StatCard.tsx`'s tonal cards) — these are deliberately fixed across tenants, not a bug; don't "fix" them by swapping in tenant tokens without checking whether that collapses distinct colors into one (several semantic tokens key off the same single `--color-primary` field).
- `booking-management/` is a self-contained feature module with its own contract — see [booking-management/AGENTS.md](booking-management/AGENTS.md).
- `auth/{Login,Register,ForgotPassword}Form.tsx` each carry their own inline Cloudflare Turnstile widget (script load, render, cleanup) and must send `turnstileToken` in their request body plus reset the widget on a **failed** submit — tokens are single-use, so replaying a burned one after a retry silently rejects otherwise-correct credentials. New auth forms should copy this inline pattern rather than importing `booking-management/hooks/useTurnstileSession` (that hook belongs to a different domain module and carries booking-management-specific `sessionStorage` behaviour).
- `admin/DataCard.tsx` is the shared mobile-row card for admin `<table>` surfaces below `lg` (`fields: {label, value}[]`, optional `title`, optional `actions` slot; chrome `rounded-[20px] border border-border bg-card shadow-sm`) — reuse it for any new table→card conversion instead of hand-rolling a card (see [../app/admin/AGENTS.md](../app/admin/AGENTS.md) for the desktop-table/mobile-card pairing convention and its DB Browser exception).
- `LanguageToggle.tsx` is the sole app-wide UI language switcher, rendered at 8 sites (client pages + `admin/AdminTopBar.tsx`) — it reads `supportedLanguages` from `useLanguage()` (`src/contexts/LanguageContext.tsx`), which is gated by the tenant's `TenantConfig.enabledLocales`, and renders nothing when only one locale is enabled. Don't hardcode `SUPPORTED_LANGUAGES` in a new switcher-like control; reuse this component/context instead.
- Header controls (Back/custom-page switcher/Language/Theme) are never `fixed`/`absolute` overlays — they render as real in-flow content so nothing can visually collide with page content beneath them (2026-08-06: this replaced a prior pattern of independently-`fixed`-positioned controls with guessed content-clearance padding, which regularly overlapped page titles on narrow screens; 2026-08-07: `legal/LegalPageHeader.tsx` was the last holdout still using `absolute` + a fixed `pt-12` content guess, and was converted for the same reason — see below). Three shapes, by whether the page can have a corner logo and/or a tab list:
  - `content/TopNavLine.tsx` (homepage, a master's own page, any custom-page view — everywhere a logo may be configured) renders `PageBackLink` first, then **breakpoint-split tab UI**: below `lg`, a burger (`DropdownMenu`, only when `tabs.length > 0`) — a tenant can configure an unbounded number of pages, which doesn't fit a horizontal strip next to Back/actions on a narrow phone; at `lg:` and up, the original horizontal scrolling tab strip (`overflow-x-auto`, framer-motion `layout` transitions, `leadingSpaceClassName` reserved-space padding) — desktop has plenty of width, so it stays as-is, **never replaced by the burger there**. `actions` (Language/Theme) sit on the right via `justify-between`; pass `backHref` to show Back at all (the true homepage passes none).
  - `leadingSpaceClassName` is real `pl-*` layout padding, but **only on the `lg:`-and-up tab strip** — never on the mobile burger/Back container, and never on the outer wrapper below `lg` (call sites' own wrapping `<div>` uses `pl-3 lg:pl-28 xl:pl-32`, i.e. zero extra offset below `lg`). Both of these were tried once each and had to be reverted same-day: applying the tab-strip's reserved padding to the burger container (Back+burger must always stay visible/clickable, unlike tab text which can scroll off-screen past the padding safely) collapsed the whole row into a sliver on mobile; leaving the outer wrapper's desktop-logo-clearance padding active below `lg` (where the logo is `hidden`) pushed Back/burger ~110-130px off the true corner for no reason. Below `lg`, a page with a logo needs it to clear the row **vertically** instead (see `HomeClient.tsx`'s mobile logo block: `pt-24`, sized to the row's tallest child — `ThemeToggle` at `h-12`+`p-2`=64px — plus the row's own `top-2` offset; a first attempt at `pt-12` undershot this by not re-measuring the actual child stack).
  - `legal/LegalPageHeader.tsx` (`privacy`, `terms`, `support`) wraps `TopNavLine` for these three no-logo pages instead of using `PageToolbar` (2026-08-06), to get the same hairline/burger treatment as home/master pages. It renders `TopNavLine` in **real document flow**, not `absolute` (2026-08-07 fix) — the earlier `absolute` version paired with a hardcoded `pt-12` on the content div below, which assumed a single-line bar; at desktop widths narrow enough for the row to wrap, the bar grew taller than that guess and the page title overlapped it. In-flow layout can't have that failure mode since content always starts after the bar's actual rendered height. This was only safe to do here (and not yet on home/master pages, which still use the `absolute` pattern) because there's no `LogoDisplay` on these pages needing to layer behind/beside the bar — see the no-`LogoDisplay` note in `LegalPageHeader.tsx` itself for why: the "home" logo bucket's position/size is tuned for the homepage's layout and collided with these pages' denser text content, and a dedicated admin-configurable bucket for three low-traffic static pages wasn't worth the new admin UI surface, so the logo is simply omitted rather than repositioned.
  - `PageToolbar.tsx` (no-logo pages: `profile`, `profile/edit`) is the simpler case — a plain in-flow flex row (`PageBackLink` + Language + Theme), no reserved-space concern since there's no logo to clear, no breakpoint split needed (there's no tab list on these pages at all).
  - `PageBackLink.tsx` is the shared Back-link markup behind all three. The old standalone `BackButton.tsx` (independently `fixed top-6 left-6`) is deleted — do not recreate it; use `PageToolbar`/`TopNavLine`'s `backHref` instead.
- `admin/content/PageListClient.tsx`/`PageFormSheet.tsx` are shared by all three content-page admin surfaces (see [../app/admin/AGENTS.md](../app/admin/AGENTS.md)): `owner: PageOwner` is the security payload forwarded verbatim to `createPage`/`reorderPages`, while `scope: "global" | "master" | "master-as-admin"` is copy-only and never used for authorization — `"master-as-admin"` plus `masterName` render the admin-on-behalf header copy.
- `admin/content/SortableList.tsx` is the single place dnd-kit is wired (render-prop `children(id, handle)`, `PointerSensor` 4px + `KeyboardSensor`, no `DragOverlay`, emits no DOM so the caller owns the container) and takes `strategy?: "list" | "grid"` (default `"list"` = `verticalListSortingStrategy` for the block/page lists, `"grid"` = `rectSortingStrategy` for the photo grid) — add a new layout there rather than instantiating a second `DndContext`. `admin/content/PhotoListEditor.tsx` is the shared photo editor behind both `Photo{Widget,Gallery}ConfigEditor` (so it renders on four surfaces: the three page block editors, `/admin/settings`'s homepage widget, and the Masters Sheet footer block) — multi-file select uploads one request per file to the unchanged single-file `/api/upload` in `UPLOAD_CONCURRENCY`-sized `Promise.allSettled` batches with per-file error lines and a single `onChange` computed from a latest-`photos` ref, ordering is drag-only via a `GripVertical` handle (arrow buttons removed; the tile itself is deliberately **not** the drag surface because `touch-action: none` on a `grid-cols-2` tile would block mobile page scroll), and the persisted shape stays a bare `string[]` with ids derived per render.
- `admin/LocalizedFieldInput.tsx` is the shared per-locale authoring field (`baseName`/`label`/`values: {pl,en,uk}`/`enabledLocales: Language[]`/`variant: "input"|"textarea"`/`resizable?: boolean`, default `false`) for `Service.name_*`/`MasterProfile.bio_*`/`TenantConfig.termsContent_*`/`privacyContent_*` — renders one plain field when only one locale is enabled, otherwise a compact tab set emitting `${baseName}_${locale}` form fields. Reuse it for any new per-locale DB column instead of hand-rolling tabs; see [../lib/AGENTS.md](../lib/AGENTS.md) for the paired `resolveLocalized`/`parseEnabledLocales` read-side helpers.
- `legal/LegalDocumentView.tsx` + `legal/MarkdownLite.tsx` are the shared public-facing renderer for both `/terms` and `/privacy` (`src/app/admin/AGENTS.md`'s content-page conventions don't apply here — these two routes stay unconditionally present, never gated). `LegalDocumentView` resolves the admin-authored `TenantConfig.termsContent_*`/`privacyContent_*` via `resolveLocalized()`: an empty result renders a translated `legal.notConfigured` empty state (never a 404 or hidden page); a fallback-locale hit (viewer's own locale empty, another locale supplied the text) shows an amber notice. `MarkdownLite` turns `src/lib/markdown-lite.ts`'s parsed node tree into React elements — never `dangerouslySetInnerHTML`.
- `src/hooks/useIsMobile.ts` is the shared `lg` (1024px, `matchMedia('(max-width: 1023.98px)')`) mobile-breakpoint hook, mirroring `useReducedMotion.ts`'s SSR-safe pattern (defaults `false`/desktop, syncs on mount + `change`). Use it wherever a component needs real conditional rendering for mobile (not just `hidden lg:*`/`lg:hidden` CSS) — the admin calendar views are the current consumers.
- Staggered list entrance animation (`MasterSelector.tsx`'s master cards, `SlotsList.tsx`'s time-slot buttons) uses the same shape: `motion.*` with `initial`/`animate` gated by `useReducedMotion()` (empty `initial`/`{duration:0}` transition when reduced-motion is preferred), `transition.delay` scaled by array index (capped, e.g. `Math.min(index, 12) * 0.03` for a list that can be long) so items cascade in rather than popping at once. `SlotsList.tsx` additionally floors its `/api/day/:date` fetch at a minimum perceived duration (`withMinDelay`, 400ms, 2026-08-07) — since availability now resolves against the local DB with no external round-trip, an unfloored fetch could resolve in single-digit ms and the loading spinner would barely flash before slots popped in with no animation to speak of. Reuse this same min-delay + stagger shape for any other "was slow via an external API, now instant via the local DB" loading state rather than leaving it un-animated.
- Files must stay under 500 lines — split large components (state, handlers, sub-panels) into siblings or a co-located folder, following the pattern already used in `booking-management/`. `DataExportModal.tsx` follows this via its co-located `data-export/` folder (`types.ts`, `exportFormat.ts`, `ExportResultView.tsx`).
- `ui/dropdown-menu.tsx` and `ui/alert-dialog.tsx` are authored against the project's **Tailwind v3** config — use base-ui's `data-[open]`/`data-[closed]` arbitrary-attribute variants (and `[var(--x)]` arbitrary values), not v4-only syntax (`data-open:`, `(--x)`, `outline-hidden`, `**:`, `not-*:`).
- `ui/alert-dialog.tsx` is the destructive-confirmation primitive (base-ui `alert-dialog`, always modal, no outside-click dismissal, `z-[100]`), driven by `ConfirmDialogProvider.tsx`'s `useConfirm(): (message, options?) => Promise<boolean>` — callers pass an already-translated message; the dialog owns only `common.confirmTitle`/`common.cancel`/`common.confirm`.
- `AppToaster.tsx` is the app's single sonner `<Toaster />` mount (rendered from `src/app/providers.tsx`); without it every `toast.*()` call is a silent no-op. Its theme follows the manual `.dark` class via `MutationObserver`, never `theme="system"`.
- `admin/discounts/*` (`DiscountListClient.tsx`/`DiscountForm.tsx`/`DiscountScopeFields.tsx`/`DiscountWindowFields.tsx`) is the shared component set for both discount admin surfaces, mirroring the `admin/content/*` convention: `owner: DiscountOwner` is the security payload forwarded verbatim to `createDiscount`, `scope: "global" | "master"` is copy-only and never used for authorization. The booking-flow promo-code UI is top-level: `BookingPromoCodeField.tsx` (collapsed code entry + Apply/Remove), `BookingPriceSummary.tsx` (struck-through original + discounted price + `-{percent}%` badge, reused by the success screens and the Telegram-bot-adjacent web summary), and `hooks/useDiscountPreview.ts` (drives `POST /api/discounts/preview`). `BookingAuthDetailsCard.tsx` was split out of `BookingForm.tsx` purely to stay under the 500-line limit before the promo-code UI was added (AD-11) — it owns its own edit-mode state, the parent keeps only the committed `name`/`phone`/`email`.
- `ThemeToggle.tsx` (client-facing light/dark switch, zero props, 9 call sites) is a deliberate, permanent exception to the "never hardcode a fallback brand asset" rule below: `TenantConfig.themeToggleIconUrl`/`darkThemeToggleIconUrl` each fall back independently to the static `public/light.png`/`public/dark.png` — there is **no** light→dark cascade (unlike `LogoDisplay.tsx`'s `darkLogoUrl || logoUrl || ...`), because the two icons are semantically different action glyphs, not the same brand mark in two colourways. The static PNGs are the permanent default, not an unmigrated brand asset — don't delete the fallback or add a cascade between the two fields. Custom icons render via a plain `<img>` (they may be admin-uploaded SVG, which `next/image` can't optimize since `dangerouslyAllowSVG` is intentionally off); the built-in PNGs stay on `next/image`, unchanged.

## Work Guidance

- i18next strings come from `src/locales/{en,pl,uk}.json` (Polish is default) — don't hardcode user-facing text. `admin/` components use the `admin.*` namespace (see [../app/admin/AGENTS.md](../app/admin/AGENTS.md) for the client/server split rule) — `"use client"` files call `useTranslation()` directly; a component shared between a Server Component caller and a client caller (e.g. `AppointmentStatusBadge.tsx`, which computes its own status label) is itself `"use client"` rather than requiring every caller to pre-translate.
- Components fetching `/api/tenant-config` via react-query use two established `queryKey`s depending on need: `['tenant-config-contact']` for the salon-contact-info subset (`support/`, `privacy/`, `terms/` pages, `BookingSuccess(Panel).tsx`), and `['tenant-config']` for branding fields like `brandName`/`logoUrl`/`darkLogoUrl` (`BrandHeader.tsx`, `Footer.tsx`, `LogoDisplay.tsx`). Match the existing key for the data you need — mixing keys defeats react-query's per-page cache dedup between components that want the same fields (`LogoDisplay.tsx` used a raw uncached `fetch` until 2026-08-07, which flashed an empty placeholder before the logo popped in on every client-side page navigation — moving it onto the shared `['tenant-config']` key fixed that, matching `Footer.tsx`'s pattern). Never hardcode a fallback brand asset (image or name) — an absent `TenantConfig` value means render nothing, with `DEFAULT_BRAND_NAME` (from `@/lib/constants/brand`) as the only acceptable text fallback.
