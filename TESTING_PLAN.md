# План тестирования — Salon Booking 2.0

Сквозной чек-лист от первого запуска на VPS до продажи первому реальному
клиенту. Иди по этапам по порядку — каждый следующий опирается на то, что
предыдущий уже настроен и работает. Ставь `[x]` по ходу, ничего не держи в
голове.

Домен подставляй вместо `<DOMAIN>` в командах ниже. Проще всего один раз
сохранить его в переменную в терминале:

```bash
DOMAIN=booking.example.com
```

## Этап 7. Проверка защиты — Turnstile, rate-limit, авторизация

Тут уже нужен терминал (curl). Все команды — против реального задеплоенного
домена, не localhost (Turnstile и Upstash не сработают локально без ключей).

### 7.1. Turnstile на `/api/book` реально блокирует

```bash
curl -s -o /dev/null -w "%{http_code}\n" -X POST "https://$DOMAIN/api/book" \
  -H "Content-Type: application/json" \
  -d '{"startISO":"2026-09-01T10:00:00+02:00","endISO":"2026-09-01T10:30:00+02:00","masterId":"<любой существующий masterId>","name":"Test","phone":"+48123456789"}'
```

Без `turnstileToken` в теле и с настроенными на сервере ключами — должно
вернуться `400` с кодом `TURNSTILE_TOKEN_REQUIRED`. Если вернулось `200` и
запись создалась — это баг, разбираться отдельно (значит проверка не
подключилась в проде, например ключи не попали в `.env`).

### 7.2. Rate-limit — таблица всех защищённых точек

Лимиты считаются по IP (кроме бота — там по chat_id, уже проверено в
Этапе 5). Самый простой способ проверить любую точку — прогнать её в цикле
чуть больше лимита и убедиться, что на последнем запросе прилетает `429`
с `{"code":"RATE_LIMITED"}`.

| Эндпоинт                                  | Лимит | Окно   |
| ----------------------------------------- | ----- | ------ |
| `POST /api/book`                          | 8     | 15 мин |
| `POST /api/bookings/cancel`               | 15    | 15 мин |
| `POST /api/bookings/update-time`          | 15    | 15 мин |
| `POST /api/bookings/update-procedure`     | 15    | 15 мин |
| `PATCH /api/bookings/[id]`                | 15    | 15 мин |
| `POST /api/bookings/[id]/check-extension` | 20    | 15 мин |
| `GET /api/bookings/all`                   | 20    | 15 мин |
| `POST /api/auth/register`                 | 5     | 15 мин |
| `POST /api/auth/forgot-password`          | 3     | 15 мин |
| `POST /api/auth/reset-password`           | 10    | 15 мин |
| `POST /api/consents/erase`                | 3     | 15 мин |
| `POST /api/consents/export`               | 5     | 15 мин |
| `POST /api/consents/withdraw`             | 5     | 15 мин |
| `POST /api/support/contact`               | 3     | 15 мин |
| `POST /api/master/contact`                | 3     | 15 мин |
| `GET /api/discounts/preview`              | 30    | 1 мин  |
| `GET /api/discounts/today`                | 60    | 1 мин  |

Пример проверки для `GET /api/bookings/all` (лимит 20/15мин — самый быстрый
для ручной проверки):

```bash
for i in $(seq 1 21); do
  curl -s -o /dev/null -w "%{http_code}\n" \
    "https://$DOMAIN/api/bookings/all?phone=%2B48000000000&name=RateLimitTest"
done
```

Ожидание: первые 20 строк — `200`, 21-я — `429`. **Важно**: если все 21
строка вернули `200` — это значит Upstash не подключён (Этап 2, доп.
пункт), и весь Этап 7.2 нужно перепройти после того, как это будет
исправлено, иначе Этап 7 фактически пройден "вслепую".

Повторить тот же принцип (цикл N+1 запросов, ждём `429` на последнем) для
`/api/auth/register`, `/api/consents/erase` — это самые дешёвые лимиты
(3-5 запросов), быстрее всего проверить руками.

### 7.3. Проверка владения записью (телефон)

```bash
curl -s -X POST "https://$DOMAIN/api/bookings/cancel" \
  -H "Content-Type: application/json" \
  -d '{"eventId":"<id реальной тестовой записи>","firstName":"Test","phone":"+48999999999"}'
```

С заведомо неверным телефоном — должно вернуться `403`
`VERIFICATION_FAILED`, запись не должна отмениться (проверить в админке).

- [ ] Открыть `/admin` и `/profile` в приватном окне браузера (без сессии) —
      должен быть редирект на `/auth/login`, а не показ страницы.
- [ ] Залогиниться под CLIENT-аккаунтом, попытаться открыть `/admin` —

### 7.5. Cron-эндпоинт и заголовки безопасности

## Этап 8. Нагрузка

Для приложения одного салона (не тысячи одновременных клиентов) цель — не
"выдержать миллион RPS", а убедиться, что обычный всплеск (несколько
человек одновременно открыли сайт/бронируют) не роняет маленький VPS-контейнер
и что защита от гонки при двойном бронировании реально работает.

### 8.1. Общая нагрузка на чтение (не требует установки — через `npx`)

```bash
npx autocannon -c 20 -d 20 "https://$DOMAIN/"
npx autocannon -c 20 -d 20 "https://$DOMAIN/api/procedures?masterId=<masterId>"
```

Смотреть на `2xx` (не должно быть массовых `5xx`/таймаутов) и на
latency p99 — для маленького VPS ожидаемо в пределах пары секунд под
нагрузкой, не десятки секунд.

### 8.2. Гонка при двойном бронировании одного слота

Проверяем, что транзакционная проверка конфликта в `createBooking()`
реально не даёт создать два пересекающихся бронирования при параллельных
запросах (защита уже в коде — тут просто подтверждаем её вживую):

```bash
for i in 1 2 3 4 5; do
  curl -s -X POST "https://$DOMAIN/api/book" \
    -H "Content-Type: application/json" \
    -d '{"startISO":"2026-09-02T12:00:00+02:00","endISO":"2026-09-02T12:30:00+02:00","masterId":"<masterId>","name":"Race Test","phone":"+4890000000'"$i"'","turnstileToken":"<если капча отключена для теста — см. ниже>"}' &
done
wait
```

Ожидание: ровно один запрос успешный (`200`), остальные — `409 CONFLICT`.
Если успешных больше одного — реальный баг с гонкой, а не просто
недостающая защита.

> Для этого конкретного теста, если Turnstile мешает (5 параллельных
> гостевых запросов без реального прохождения виджета), проще временно
> протестировать под залогиненным клиентом (капча не требуется) или
> временно снять `TURNSTILE_SECRET_KEY` из `.env` тестового инстанса на
> время этого одного теста — не забыть вернуть обратно.

## Этап 9. GDPR (самообслуживание клиента)

Через `/support` на реальном домене:

- [ ] **Экспорт данных** — ввести телефон реальной тестовой записи,
      получить файл/письмо с данными, проверить что все связанные записи
      в нём есть.
- [ ] **Удаление данных** — то же самое, подтвердить, зайти в
      `/admin/database/gdpr` и убедиться, что телефон/имя анонимизированы
      (хэш телефона, не текст), а сама запись (appointment) осталась для
      статистики салона.
- [ ] **Отзыв согласия** — отдельно от удаления, проверить что новое
      бронирование тем же контактом снова просит подтвердить согласие.

## Этап 10. Финальный чек-лист перед первым реальным клиентом

- [ ] Этапы 0–9 пройдены на одноразовом тестовом VPS без открытых пунктов.
- [ ] Тестовые данные (мастера/записи/скидки) с тестового VPS никак не

      `install.sh --name=<client-slug>` запуск.
- [ ] `CREDENTIALS.txt` с тестового инстанса удалён (`rm`), сам тестовый
      VPS выключен/уничтожен, если он был одноразовым.

      общий, если так решили — см. пояснение в чате про Upstash) и **свой**

      вёрстки при смене языка на странице мастера — не блокер, но клиенту
      можно заранее сказать, что это мелкий косметический момент.

## Чего в этом плане нет (осознанно)

- Автоматизированного бэкапа/восстановления БД — деплой-тулинг сейчас его
  не делает вообще (ни ручного, ни по расписанию). Не часть сегодняшнего
  плана, но стоит держать в уме как следующий пункт бэклога перед тем, как
  на инстансе появятся реальные деньги/клиенты салона.
- Полноценного пентеста (SQL-инъекции, XSS и т.п.) — это уже другая
  дисциплина; текущий план проверяет то, что мы явно достраивали и
  меняли (капча/лимиты/владение записью), не весь периметр целиком.
