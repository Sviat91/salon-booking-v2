# План: автоматизация продаж Salon Booking (холодный аутрич)

Дата составления: 2026-08-09. Это стратегический blueprint, не код. **Ни одна строка
кода Salon Booking здесь не меняется.** Сама автоматизация будет отдельным проектом
на сервере (отдельный linux-юзер), этот файл — карта того, что и в каком порядке
строить.

Читать сверху вниз. Раздел 1 (риски) — самый важный, вся архитектура крутится
вокруг него. Ставь `[x]` по ходу.

---

## 0. Цель и рамки

- **Что продаём:** SaaS-систему бронирования для салонов (мультитенант, онлайн-запись,
  Telegram-бот для клиентов, скидки/промокоды, GDPR, брендирование под клиента,
  one-command деплой на VPS).
- **Кому:** салоны красоты / барбершопы / парикмахерские / ногтевые студии.
  Гео — сначала **Варшава**, потом вся Польша. Язык владельцев — **польско-,
  русско- и украиноязычные, все**.
- **Канал:** холодный Instagram Direct (основной) + email (вторичный, для тех, у кого
  нет достижимого IG).
- **Философия (жёстко):** агент только **находит** лиды и **пишет первое** сообщение.
  Агент **никогда не ведёт переписку**. Пришёл ответ → уведомление тебе в Telegram,
  дальше общаешься **ты руками**.
- **Бюджет:** близкий к нулю. Максимум — бесплатные тиры и Google-кредит. Платные
  подписки — только если без них никак, и осознанно.
- **Контроль:** ты рулишь всем через приложение (Claude Code на сервере в tmux),
  запуск по cron, отчёты в отдельный Telegram-бот.

**Что НЕ входит на старте:** агент не отвечает на ответы; авто-постинг контента —
отложен (раздел 12); TikTok — опция на потом.

## 1. Риски и как ими управляем (читать первым)

| # | Риск | Насколько серьёзно | Митигация |
|---|------|--------------------|-----------|
| R1 | **Бан IG-аккаунта.** Свежий аккаунт + резкий объём/скорость = блок за часы. | Высокий, самый вероятный | Прогрев до автоматизации (нед. 0); медленный ramp-up; дневные лимиты; человекоподобные задержки; стоп при первом challenge (раздел 5, 9). **Важно:** любые действия под логином (поиск/просмотр профилей), не только отправка, считаются автоматизацией — тяжёлый IG-поиск выносить на отдельный read-only аккаунт (раздел 6, M2). |
| R2 | **`instagrapi` ломается** при обновлении IG (неофициальный приватный API). | Средний, периодический | Вся работа с IG изолирована в 1-2 модуля (M5/M6); ошибки логируются и уведомляют тебя; ручной фолбэк «агент готовит — ты шлёшь». |
| R3 | **Нарушение ToS Instagram.** Холодная авторассылка через приватный API — это серый/чёрный метод по правилам Meta. | Юридически на нас | Осознанное решение. Один расходный аккаунт, готовность пересоздать. Не привязывать к личному номеру/личному профилю. |
| R4 | **Один аккаунт = контент + рассылка.** Бан бьёт по всему присутствию сразу. | Средний | Принято тобой осознанно. Компромисс: рассылка идёт с брендового аккаунта (выглядит живее), но при бане теряем и витрину. Держать бэкап контента отдельно, чтобы быстро поднять новый. |
| R5 | **Google $300-кредит / биллинг.** Кончится кредит или неаккуратный field-mask → счёт. | Низкий при аккуратности | Минимальный field-mask (раздел 4); дедуп (не запрашивать одно и то же дважды); алерт на расход кредита. |
| R6 | **Спам-качество.** Одинаковые/шаблонные сообщения = жалобы, флаги, репутация. | Средний | Реальная персонализация под каждый салон; вариативность текста; ссылку — не в первом сообщении; ручной ревью первых партий. Раздел 8. |
| R7 | **GDPR/PECR по холодному B2B-email в EU.** | Низко-средний | Только публичные бизнес-контакты, только B2B, obязательный opt-out, не физлицам. Раздел 13. |

**Золотое правило:** на старте всё делается медленнее и меньше, чем хочется. Резкий
скачок активности у нового аккаунта — причина бана №1, раньше, чем сам объём.

## 3. Архитектура пайплайна

Поток данных, слева направо. Каждый этап — отдельный модуль-инструмент, который дёргает агент.

```
A. Discovery      B. Enrichment        C. Store            D. Message         E. Outreach        F/G. Feedback
(Google Maps)  →  (найти IG,        →  (БД лидов,       →  (генерация     →   (instagrapi DM  →   (Telegram отчёт
salon+address     язык, контакты)      статусы,            персонального       + email фолбэк,     + детект ответов
+phone+website                         дедуп)              текста)             лимиты/задержки)    → уведомление)
```

**Центральный принцип — дедуп.** У каждого лида уникальный ключ (`place_id` от Google
и/или IG `username`). Статус лида двигается по конвейеру и **никогда не откатывается на
повторный контакт**. Одному салону пишем ровно один раз.

**Модель данных (таблица `leads`, SQLite — как в основном проекте):**

| Поле | Назначение |
|------|-----------|
| `id` | PK |
| `dedup_key` | UNIQUE — `place_id` или нормализованный IG `username` |
| `source` | `gmaps` / `ig` / `apify` |
| `name`, `category` | название и тип салона |
| `address`, `city`, `district` | адрес, город, район |
| `phone`, `website`, `email` | контакты |
| `ig_username`, `ig_url` | инстаграм |
| `language` | `pl` / `ru` / `uk` / `unknown` |
| `web_state` | `none` (нет сайта) / `info_only` (сайт без онлайн-записи) / `broken` (мёртвый домен/не грузится/протух) / `has_booking` (уже есть система записи) — **сигнал квалификации, раздел 4** |
| `priority` | `hot` / `warm` / `cold` — по `web_state` (см. раздел 4) |
| `status` | `new` → `enriched` → `queued` → `contacted` → `replied` / `skipped` / `bounced` |
| `channel_used` | `instagram` / `email` — выбираем по достижимости, не «IG всегда первым» |
| `message_sent` | фактически отправленный текст (для аудита/анти-повтора) |
| `contacted_at`, `replied_at` | таймстемпы |
| `notes` | ручные пометки |
| `created_at`, `updated_at` | служебные |

## 4. Гео и языковая сегментация (решение проблемы региона)

Проблема, которую ты поймал: у IG keyword/hashtag-поиска **нет гео-фильтра**. Решение —
**Google Maps как основной источник** (там гео-поиск настоящий), IG — вторичный.

**Стратегия запросов к Places API:**
- Text Search (New): `textQuery` вида `"salon fryzjerski Warszawa Mokotów"` — сетка
  (ключевое слово × район Варшавы), либо Nearby Search с `locationRestriction`
  (круг: центр района + радиус) и `includedTypes`.
- Типы мест (Places New): `beauty_salon`, `hair_care`, `nail_salon`, `spa`, `barber_shop`.
- Ключевые слова PL: `salon urody`, `salon fryzjerski`, `barber`, `paznokcie`,
  `kosmetyczka`, `brwi i rzęsy`, `salon kosmetyczny`, `stylizacja`.
- Пагинация: `nextPageToken`, до ~60 результатов (3 страницы) на запрос.
- **Экономия кредита:** минимальный `fieldMask` — только `displayName`,
  `formattedAddress`, `nationalPhoneNumber`, `websiteUri`, `location`, `primaryType`.
  `websiteUri`/phone — дорогой Enterprise-SKU, но при наших объёмах $300 хватит с запасом.

**Языковая сегментация (на этапе Enrichment, не Discovery):**
- Эвристика по тексту (название + IG-био): кириллица → `ru`/`uk`; наличие
  специфически украинских букв `є/ї/і/ґ` → `uk`, иначе `ru`; латиница/польские
  диакритики → `pl`.
- Уточнение: агент-LLM классифицирует язык био, когда эвристика неоднозначна.
- Русско/украиноязычные салоны обычно палятся кириллицей в био/постах и славянскими
  именами владельцев.
- Язык — только для выбора языка сообщения. **По языку НЕ приоритезируем** (решено):
  валим по всем равномерно.

### Квалификация лидов — по состоянию веб-присутствия (ключевой фильтр)

Не все салоны одинаково хорошие лиды. **Наш идеальный клиент — салон, у которого
онлайн-присутствие заброшено или неполноценно.** Наличие сайта само по себе НЕ
дисквалифицирует — важно его состояние. На этапе Enrichment (M2), когда всё равно
тянем сайт, классифицируем `web_state` → `priority`:

| `web_state` | Что значит | `priority` | Логика |
|-------------|-----------|-----------|--------|
| `none` | Сайта нет, только IG/FB | **hot** | Нужен и сайт, и запись — прямое попадание |
| `broken` | Домен протух / не грузится / мёртвый SSL | **hot** | Про них забыли, никто не занимается — лёгкая победа (реальный кейс: салон с протухшим доменом) |
| `info_only` | Сайт есть, но онлайн-записи нет (только телефон/часы) | **hot** | Наш основной оффер — добавить онлайн-запись |
| `has_booking` | Уже есть рабочая система записи (Booksy/Reservio/своя) | **cold** | Уже обслужены. Не выкидываем совсем — отдельный поздний сегмент с другим оффером («своя система без комиссий Booksy»), но НЕ на старте |

- Детект `has_booking`: искать на странице маркеры — `booksy`, `reservio`,
  `versum`, `moment`, `calendly`, виджеты записи, `zarezerwuj online` / `umów wizytę`.
- **Порядок работы аутрича:** сначала `hot`, потом `warm`, `cold` — в самом конце
  или никогда на старте. Это поднимет конверсию сильнее любой правки текста —
  пишем тем, кому реально нужно.

## 5. Фаза 1 — IG-аккаунт: создание и прогрев (ДО автоматизации)

Это делается руками, с телефона, до любого кода. **Не логиниться в `instagrapi` с VPS в
первые дни** — сначала аккаунт должен пожить с реального устройства/IP.

- [ ] Создать Gmail проекта (почта для IG-аккаунта и email-аутрича).
- [ ] Создать IG-аккаунт. **Personal подойдёт** (`instagrapi` не требует Business).
      Привязать к Gmail проекта и к отдельному номеру (не к личному профилю).
- [ ] Оформить: аватар, имя, био (что делаем + оффер одной строкой + ссылка на демо),
      6–9 стартовых постов (скриншоты сайта, короткие видео фич — «настройка за минуту»,
      «онлайн-запись», «Telegram-бот»), 1–2 reels, highlights.
- [ ] Включить 2FA. **Важно для `instagrapi`:** логин session-based — сохранять
      session-файл, не логиниться заново каждый раз (частые ре-логины = флаг).
- [ ] **Прогрев ~1–2 недели**, руками с телефона: заходить ежедневно, лайкать,
      смотреть stories, подписываться на 5–10 релевантных аккаунтов/день, постить
      регулярно. Цель — накопить историю и «траст» до автоматизации.
- [ ] Собрать бэкап контента (посты/видео/тексты) отдельно — чтобы при бане быстро
      поднять новый аккаунт.

## 6. Фаза 2+ — модули автоматизации

Каждый модуль — отдельный скрипт/инструмент, который агент вызывает. Строить и проверять
**по одному**, в этом порядке.

- **M1 `gmaps_search`** — обёртка Places API. Вход: ключевое слово + район/город. Выход:
  сырые лиды в БД со статусом `new`.
- **M2 `enrich_lead`** — по каждому `new`-лиду. Если есть `websiteUri` — **один раз
  тянем сайт** и снимаем с него сразу три вещи (бесплатно, без действий с IG-аккаунта):
  1. **IG-ссылку** — ищем `instagram.com/…` (часто в футере; иногда `websiteUri` =
     сразу ссылка на их IG).
  2. **`web_state`** (раздел 4) — грузится ли вообще (мёртвый/протухший → `broken`);
     есть ли маркеры системы записи (`booksy`/`reservio`/`versum`/`umów wizytę` →
     `has_booking`); иначе `info_only`. Нет сайта вовсе → `none`. Проставляем `priority`.
  3. **Email** — `mailto:` / видимый контактный адрес на странице (Google Maps email
     не отдаёт). Опционально Hunter.io, но его free-тир мал (~25/мес) — не основной
     путь, только точечно.
  Если IG со страницы не нашёлся и сайта нет:
  4. **IG user-search** — `instagrapi` по «название + город», лучший матч по
     био/локации. **Внимание:** действие под логином, грузит «бюджет доверия»
     аккаунта — тяжёлый поиск выносим на отдельный **read-only** аккаунт (не тот,
     что шлёт DM; забанят — не жалко, пишем всё равно с брендового).
  5. **Apify** — опциональный бэкап для более глубоких данных без нагрузки на аккаунты.
  Затем язык, `enriched`, и **выбор канала по достижимости**: есть IG → `instagram`;
  нет IG, но есть email → `email` (M7); ни того, ни другого → `skipped`.
- **M3 `leads_db`** — хранилище + дедуп + переходы статусов. Единственный владелец
  `dedup_key`. Никакой модуль не пишет лид напрямую в обход него.
- **M4 `message_gen`** — генерация персонального сообщения. Делает сам агент-LLM по
  брифу/шаблону (раздел 8): язык лида, упоминание специфики салона, оффер, мягкий CTA.
- **M5 `ig_send`** — `instagrapi`: логин с сохранением session, `send_dm`, дневной
  лимит, рандомные задержки, «рабочие часы», **стоп при challenge/лимите**. Ставит
  `contacted` + сохраняет `message_sent`.
- **M6 `ig_inbox`** — `instagrapi`: чтение `direct_threads` / pending inbox, детект
  новых входящих относительно last-seen state, ставит `replied`, дёргает M8.
- **M7 `email_send`** — Gmail SMTP, фолбэк для лидов без достижимого IG. Obязательный
  opt-out в подписи.
- **M8 `tg_report`** — Telegram-бот: сводка по проходу + мгновенное уведомление об
  ответе.
- **M9 `orchestrator`** — cron-запускаемый связующий модуль: соблюдает дневные лимиты,
  ведёт state, разносит проходы по времени, пишет логи.

**Про «несколько агентов» (найти → отсортировать → рассылать).** Как разделение
обязанностей — правильная мысль, и она уже отражена: поиск+обогащение (M1/M2),
квалификация (`web_state`/`priority`), рассылка (M4/M5) — это три разных этапа.
**Но реализовывать это лучше не как три постоянно-живущих агента, которые болтают
друг с другом, а как отдельные стадии по cron, у которых точка обмена — сама таблица
лидов** (ровно твоё «складываем в таблицу, дальше обрабатываем»): стадия A пишет
лиды со `status=new`, стадия B берёт `new` → квалифицирует → `enriched/queued`,
стадия C берёт `queued` hot-лиды → пишет. Таблица и статусы — очередь между стадиями.
Это дешевле (меньше вызовов модели), проще дебажить и переживает падение любой стадии.
Финальное решение (субагенты vs стадии-скрипты) — на этапе стройки на сервере.

## 7. Инфраструктура на VPS

- [ ] Отдельный linux-юзер (изоляция от Salon Booking — разные права, разные директории).
- [ ] Отдельная директория проекта + свой Python venv.
- [ ] tmux-сессия с Claude Code — чтобы подключаться и контролировать с телефона.
- [ ] cron: разнести проходы по времени суток — Discovery-проход, Outreach-проход
      (в «рабочие часы»), Inbox-проход (несколько раз в день).
- [ ] Секреты в `.env` (chmod 600), **не логировать** (тот же AD-7 паттерн, что в
      основном проекте: пароли/токены/session никогда не в stdout/логи).
- [ ] Логи каждого прохода (что нашли, кому написали, ошибки).
- [ ] **Вопрос IP/proxy (раздел 12):** логин в IG со стабильного PL-IP снижает R1.
      VPS может быть не в Польше — решить, нужен ли residential/mobile PL-proxy на старте.

## 8. Оффер и сообщения

- **ОФФЕР (определён 2026-08-09):** два пакета, гео — только Польша пока.
  - **A. Self-host:** **500 zł единоразово** за установку. Клиент получает

  - **B. Managed (мы хостим):** **500 zł установка + 50 zł/мес** (≈10 €) —
    включает хостинг с нашей стороны, поддержку и выкат будущих обновлений.
  - **Free-установка за отзыв — только по установке.** Первым 5–10 клиентам
    установку делаем бесплатно/со скидкой в обмен на отзыв/кейс. Если они хотят
    managed-хостинг — 50 zł/мес всё равно платят (бесплатна только разовая
    установка, не хостинг). Это надо явно прописать в оффере.
  - **Экономика подписки — намеренно так.** 50 zł/мес выглядит «едва покрывает
    VPS», и в этом вся соль: дёшево для клиента = низкий барьер, а прибыль идёт
    с **плотности**. Проект специально мультитенантный (несколько инстансов на
    один VPS). Один VPS ~10 €/мес держит **минимум 30, до ~50 инстансов** → при
    30–50 клиентах это ~1500–2500 zł/мес выручки на ~40 zł/мес расходов VPS.
    На плотности маржа отличная, а не тонкая.
  - **Управляемость (плюс этой модели).** Таблица «клиент → сервер». Обновления:
    дорабатываешь локально → пушишь в GitHub → один скрипт проходит по всем
    контейнерам (git pull + rebuild + restart). Managed-хостинг становится
    дешёвым в эксплуатации, а не обузой.
  - Домены: большинство нормальных салонов уже имеют домен. Мы домены **не
    покупаем** за клиента (это его расход) — но можем помочь подключить. Для
    self-host домен+хостинг целиком на клиенте.
- **Будущая монетизация (направление, НЕ сейчас):** сверху базовой системы —
  доп-функции, часть бесплатных, часть платных (напр. AI-агент/консультант на
  сайт салона, AI-рассылки). Для AI **не подписка** (подписки сложно просчитать
  под непредсказуемый расход, да и «всех задолбали») — а **перепродажа токенов с
  небольшой наценкой**, клиент сам выбирает модель/цену. Далёкое будущее, но
  вектор — так.
- **Структура первого сообщения:** короткое, персональное (упомянуть их салон/нишу) →
  1 конкретная выгода (не список фич) → мягкий оффер → лёгкий CTA («интересно — покину
  короткое демо / пример»), НЕ «купи».
- **3 языка (PL/RU/UK):** шаблоны-каркасы + слоты персонализации, текст варьировать.
- **Анти-спам гигиена:** ссылку **не** в первом DM (IG режет доставляемость и флагует
  за ссылки от новых аккаунтов) — ссылка в био или во втором касании; не слать
  идентичный текст подряд; демо показывать по запросу.
- **Демо (решено 2026-08-09):** отдельный **чистый** демо-инстанс. Текущий
  `salon.nodayoby.online` не годится — он тестовый, забит тестовыми данными.
  Взять дешёвый домен (~$1–2/год), пересадить/поднять на нём чистый демо для
  ссылок в аутриче. Возможно ещё один демо позже.
- **A/B:** 2–3 варианта первого сообщения, смотреть отклик, оставить лучший.

## 9. Расписание и объёмы (ramp-up)

| Период | Аутрич | Примечание |
|--------|--------|-----------|
| Неделя 0 | 0 | Создание + прогрев + контент (раздел 5) |
| Неделя 1 | 5–10 DM/день | Первые партии — ручной ревью текстов ДО отправки |
| Неделя 2 | 10–20/день | Если ноль признаков challenge |
| Неделя 3+ | 20–30/день | Потолок 30 (твоё решение) |

**Правила поведения M5:**
- Рандомные задержки между сообщениями (5–15 мин, не фиксированные).
- Только в «рабочие часы» (напр. 10:00–19:00 по PL), не 24/7.
- **Выходные — шлём (решено 2026-08-09):** без паузы, не тормозим.
- **Без приоритета языков (решено 2026-08-09):** валим по всем (PL/RU/UK) равномерно,
  без очередности.
- При первом же challenge / temporary block — **немедленный стоп**, уведомление тебе,
  ручной разбор, снижение объёма после.
- Расчёт по твоей математике: 30/день × ~2–10% ответов = 1–3 живых диалога/день —
  комфортно отрабатываешь руками.

## 10. Метрики и контроль

- **Трекаем:** найдено → обогащено → отправлено → ответы → демо → продажа (воронка).
- **Telegram-сводка** после каждого прохода: `нашли X / написали Y / ответов Z`.
- **Ручные чек-поинты:** несмотря на «postfactum» — **первую партию (нед. 1) смотришь
  ДО отправки**. Дальше переходишь на постфактум-ревью.
- Еженедельно: смотреть конверсию по языкам/районам/тексту, отключать то, что не заходит.

## 13. Юридика и этика (коротко и честно)

- **Instagram ToS:** холодная авторассылка через приватный API — против правил Meta,
  риск на нас (R3). Идём осознанно, одним расходным аккаунтом.
- **GDPR / PECR (EU, Польша) по холодному email:** публично опубликованный **бизнес**-
  контакт + строго **B2B** + obязательный **opt-out** в каждом письме — как правило
  допустимо; **физлицам не писать**, лишние перс. данные не хранить.
- **Инстаграм-DM** в EU в явный «email-маркетинг» по PECR не попадает, но health/etika
  та же: не спамить, персонализировать, уважать «нет».

## 14. Чего в этом плане нет (осознанно)

- Готового кода/агентов — по твоему решению всё строится потом, на сервере.
