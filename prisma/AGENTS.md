# AGENTS.md — prisma

## Purpose

Data model and migration history for the SQLite (libSQL) database at `prisma/app.db`.

## Ownership

`schema.prisma` (models: `User`, `MasterProfile`, `Service`, `MasterService`, `ConsentRecord`, `Schedule`, `Appointment`, `DateOverride`, `TenantConfig`, `TelegramNotificationRecipient`, `NotificationBot`, `NotificationBotMaster`, `NotificationBotRecipient`, `NotificationLog`, `NotificationTemplate`, `PasswordResetToken`, `Account`, `Discount`, `DiscountService`, `DiscountRedemption`, `CalendarSyncTask`, `ExternalCalendarBlock`) and the `migrations/` history.

## Local Contracts

- SQLite has no native enums — role (`CLIENT|MASTER|ADMIN|SUPERADMIN`), appointment status, etc. are plain `String` columns validated at the application layer, not the DB layer. Don't add a Prisma `enum`.
- `User.password`/OAuth tokens, `User.passwordEncrypted`, and `TenantConfig` SMTP/OAuth secrets must be written through `src/lib/encryption.ts` — never add a migration that stores a new secret field in plaintext. (`User.passwordEncrypted` — added 2026-07-14 — stores each master's current password **encrypted at rest** via `encrypt()`, alongside the bcrypt `password` hash used for login; decryptable on demand by ADMIN/SUPERADMIN via the `getMasterPassword` server action in `src/app/admin/masters/actions.ts`.)
- `User` identity for clients is the `(phone, name)` pair (see schema comment on `User`) — two people sharing a phone get separate rows; email uniqueness for admin/master auth is enforced in the register endpoint, not a DB constraint.
- Any schema change requires `npx prisma migrate dev --name <name>` — never hand-edit `migrations/` or `app.db` directly.
- `Service.name` and `MasterProfile.bio` are per-locale columns, not translations tables: `name_pl`/`name_en`/`name_uk` (`name_pl` is NOT NULL — the canonical default) and `bio_pl`/`bio_en`/`bio_uk` (all nullable). `TenantConfig.termsContent_pl/en/uk` and `TenantConfig.privacyContent_pl/en/uk` follow the same per-locale-column pattern but are **all six nullable, no `@default`** (unlike `name_pl`) — new installs ship with no legal text and no locale is privileged; see `src/lib/markdown-lite.ts` for how the stored Markdown-subset text is rendered. `TenantConfig.enabledLocales` is a JSON string array (default `["pl","en","uk"]`) gating which locales an admin can author. Resolve a display value with `resolveLocalized()`/`parseEnabledLocales()` from `src/lib/localized-content.ts` — never read the bare `name`/`bio` fields (they no longer exist).
- `Appointment.clientLanguage String @default("pl")` (NOT NULL) stores the client's UI language at booking time, validated against `SUPPORTED_LANGUAGES` and defaulted to `pl` by `POST /api/book` for missing/invalid input — never written directly from an unvalidated request field. Used only by `src/lib/notifications/index.ts` to pick the language of the **client-facing** confirmation/reminder copy; admin/salon-facing copy always stays `DEFAULT_LANGUAGE`.
- `TelegramNotificationRecipient` (`id`, `chatId`, `label?`, `createdAt`) is **legacy and unreferenced by application code** as of 2026-09-23 — it paired with the old single `TenantConfig.telegramBotToken` general-bot mechanism, which has been fully replaced by `NotificationBot`/`NotificationBotRecipient`. Its rows were copied (not deleted) into `NotificationBotRecipient` by `20260923090000_unify_general_telegram_bot`; the model/table are kept only as a data-preserving artifact, per the no-destructive-migration constraint — do not add new code paths that read or write it.
- `NotificationBot` (`id`, `label`, `token` — encrypted, `username?`, `enabled`, `scope`: `"ALL" | "SELECTED"`, `ownerId?` — `null` = admin/salon-owned, filled = that master's own bot, mirroring `Service.masterId`/`Discount.masterId`) is the **only** salon Telegram notification mechanism as of 2026-09-23; `NotificationBotMaster` (`botId`, `masterId`, `@@unique([botId, masterId])`) scopes a `SELECTED` bot to specific masters, `NotificationBotRecipient` (`botId`, `chatId`, `label?`) holds its chat-ID list. See `src/lib/AGENTS.md`'s `notifications/` bullet for the dispatch side (`bots.ts`). The migrated legacy row (fixed id `legacy_general_bot`) may hold a **plaintext** `token` — copied verbatim from `TenantConfig.telegramBotToken` rather than re-encrypted, because SQL cannot call `encrypt()` (AES-GCM keyed off `AUTH_SECRET`); this is safe because `encryption.ts`'s `decrypt()` passes through any non-`iv:authTag:data` string unchanged, so a one-colon Telegram token decrypts correctly either way, and the row is re-encrypted automatically the first time it's edited through the bot card. `TenantConfig.telegramBotToken`/`telegramBotUsername` are dual-purpose — they also back the Telegram login widget (`api/auth/[...nextauth]/route.ts`) — and must **never** be nulled or removed by any future notification-side migration.
- `TenantConfig`'s SMS columns (`notifSmsEnabled`, `smsProvider` — `"twilio" | "smsapi"`, `twilioAccountSid`, `twilioAuthToken`, `smsApiToken` — all encrypted via `src/lib/encryption.ts`; `twilioFromNumber`/`smsApiSender` stay plaintext since they're displayed on the recipient's handset, not secrets) added 2026-08-23 alongside `NotificationTemplate`. `NotificationTemplate` (`id`, `type`, `language`, `channel`, `body`, `createdAt`, `updatedAt`, `@@unique([type, language, channel])`) is admin-editable notification body text — **one row per `(type, language, channel)`**, and an **absent row means "use the built-in default"** (`src/lib/notifications/templates.ts`'s `DEFAULT_REMINDER_BODIES`); the table is never seeded/backfilled, and saving an empty body from the admin editor deletes the row (that is how "reset to default" works). `channel` now holds all three values (`sms | email | telegram`, `ReminderChannel` in `src/lib/notifications/templates.ts`) as of 2026-08-23 — the column landed **without a migration**, exactly as it was designed for (a plain `String` with no enum/check/default from day one).
- `Appointment.originalPrice`/`finalPrice`/`discountId` are a **nullable snapshot** written by all three `appointment.create` sites (`booking-service.ts`, `master/appointments`, `admin/calendar/appointments`); `null` means "pre-discounts row" and readers fall back to the live `MasterService.priceOverride ?? Service.price` via `resolveAppointmentPrice()` (`src/lib/discounts/shared.ts`) — there is no backfill. `Discount.masterId` mirrors `Service.masterId` semantics (`null` = admin/global, filled = that master's own). `Discount.code` is stored uppercase-normalized via `normalizeDiscountCode()` — that is what makes the `@unique` index case-insensitive on SQLite. `label`/`percent` are deliberately **not** denormalized onto `Appointment` — `Appointment.discountId` is `onDelete: SetNull`, so deleting a `Discount` drops the join but the percentage stays derivable from the price snapshot (`discountPercentFromSnapshot()`).
- Google Calendar sync (2026-09-21): `Appointment.googleEventId` (nullable; `null` = never pushed) is the id of the mirrored event; `MasterProfile.googleCalendarId`/`googleSyncToken`/`googleSyncStatus`/`googleSyncError`/`googleSyncedAt` are per-master connection state (null/empty `googleCalendarId` = not connected). `CalendarSyncTask` is the push outbox — **one row per appointment** (`appointmentId @unique`, deliberately no FK so it survives a hard delete); a DELETE overwrites a pending UPSERT and is never followed by one. `staleCalendarId`/`staleGoogleEventId` (nullable, added by `20260921130000_google_calendar_push_fixes`) carry the previous master's event when an admin PUT reassigned the appointment: `processSyncTask` deletes it first, and a later plain re-enqueue never clears them. Outbox completion/backoff writes are guarded by `updatedAt` (lost-update protection). `TenantConfig.googleServiceAccountKey` is encrypted via `src/lib/encryption.ts`; `googleServiceAccountEmail` is deliberately plaintext (masters must be told whom to share with).
- `ExternalCalendarBlock` (added by `20260921140000_external_calendar_blocks`) is the read-only mirror of an event created directly in Google: same `date`/`startTime`/`endTime` convention as `Appointment` (date = UTC midnight of the Warsaw-local day, times = Warsaw wall-clock `HH:MM`), **one row per local day** (`@@unique([masterId, googleEventId, date])`), no client/service/price. `title`/`description` hold the raw Google text or `null` — the localized fallback is applied at display time and never stored. `conflictNotifiedAt` dedups the conflict notice and is cleared when the block's times change. Cascades with the master `User`. `NotificationLog.type` also holds `CALENDAR_CONFLICT` (comment-only change, no migration — plain `String`).

## Work Guidance

- After a migration that changes procedure/schedule-related tables, remember cache invalidation is a separate manual step in the calling code (`src/lib/cache.ts` keys) — Prisma migrations don't touch Redis.
- There is no seed script (removed 2026-07-13 — `seed.ts`/`seed.js` hardcoded a `admin@somique.com`/`password123` SUPERADMIN plus a demo master account, unused by any automated path but a landmine if ever run against a real deployment). To bootstrap the first admin, use `scripts/create-admin.ts` (see `../scripts/AGENTS.md`); create a demo master through the admin panel after that.
- `DATABASE_URL`'s relative sqlite path (`file:./prisma/app.db`) resolves relative to `schema.prisma`'s own directory, not the repo root — the live dev database is actually `prisma/prisma/app.db`, not the empty stray file at `prisma/app.db`. Back up/inspect the right file. `prisma migrate dev --create-only` also requires an interactive TTY when a column change would drop non-null data (e.g. adding a required column); in a non-interactive shell, generate the raw SQL instead with `npx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --script`, hand-edit the `INSERT...SELECT` to preserve data, place it in a manually created timestamped `migrations/<ts>_<name>/migration.sql`, then run plain `npx prisma migrate dev` to apply it.

## Verification

- `npx prisma studio` to inspect data manually after a migration.
- `tests/app/api/**` mock `@/lib/prisma` (see `vi.mock`) rather than hitting a real DB — a schema change needs the mocks updated to match the new shape, not just the migration.
